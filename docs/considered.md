# Considered but skipped or deferred

Models that were evaluated for inclusion and intentionally left out (or deferred to a later rig pass), with the reason. The bar lives in `harness.py`'s scope: must install cleanly cross-platform in a self-contained venv, fit the runner protocol (text in → wav out, single process), and have a license that permits redistribution of benchmark results. CPU support is preferred but no longer required as of 2026-05-24 — CUDA-only models can be added if they fail gracefully on non-CUDA rigs.

A 2026-05-24 update added a Linux-3090 rig to the bench. Several entries below were originally skipped because of Windows-only blockers (vLLM Blackwell wheels, Linux-only compiled extensions, etc.); those become re-evaluable on the Linux rig and are flagged below where applicable.

## Future enhancement (queued, not yet implemented)

- **[VibeVoice-Large 9B](https://huggingface.co/aoi-ot/VibeVoice-Large)** (Microsoft's 9B variant, redistributed under MIT via `aoi-ot/VibeVoice-Large` and `vibevoice/VibeVoice-7B` — same weights, two naming conventions: "7B" labels by Qwen2.5-7B LLM backbone count, "9B" by total params including audio components). ~20-24 GB VRAM at fp16. Fits Win-5090 (32 GB) comfortably, **borderline on Linux-3090 (24 GB)** — KV cache for our 100+ token prompts may push it over. Fails Mac M4 (16 GB). For now we ship VibeVoice-1.5B (3B total, ~7 GB VRAM) as the cross-rig mid-tier addition; Large 9B is the quality-ceiling future enhancement, gated on either (a) confirming the 3090 fits the model with our prompts or (b) shipping a 4-bit quantized GGUF variant (community has `FluffyBunnies/vibevoice-onnx-int4` and `callgg/vibevoice-bf16` as candidates).

- **[Fish Audio S2 / S2-Pro](https://github.com/fishaudio/fish-speech)** (current `main` branch, 4B params). **Reclassified 2026-05-24 from skipped to queued for the Linux-3090 pass.** Prior block was "Linux/WSL only per official docs; Windows native unsupported" — that's resolved on a native Linux rig. 24 GB VRAM floor barely fits the 3090. Still needs a Python wrapper to orchestrate the 3-stage CLI pipeline (DAC encode → text2semantic → DAC decode) so the runner sees `text in → wav out`. Wrapper is ~1-2 days of work. Will run on Linux-3090 only; Win + Mac rows show fail (documented). Research-license non-commercial (benchmark redistribution OK).

- **[MOSS-TTS-Realtime](https://github.com/OpenMOSS/MOSS-TTS)** (OpenMOSS, 1.7B, `MossTTSRealtime` architecture, Apache 2.0). Streaming/real-time TTS for low-latency voice agents — upstream advertises a TTFB of 180 ms via incremental synthesis with multi-turn context. Needs a streaming-bench lens (sub-sentence latency, time-to-first-chunk, mean inter-chunk gap) which our current harness doesn't measure. A non-streaming wrapper would understate the model's design point — the 180 ms claim only shows up when the harness watches the first audio frame rather than the full tensor. Queued behind the "streaming bench lens" future enhancement (see [tasks.md](tasks.md)). The non-realtime siblings MOSS-TTS-Nano (100M) + MOSS-TTS flagship (8B) are in the harness as of 2026-05-25.

- **[MOSS-TTSD / MOSS-VoiceGenerator / MOSS-SoundEffect](https://github.com/OpenMOSS/MOSS-TTS)** (OpenMOSS, 1.7B-8B, Apache 2.0). Three sibling models in the MOSS-TTS family with different task shapes:
  - **MOSS-TTSD** is a *dialogue* model (multi-speaker, ultra-long dialogues). The harness's `(text in → wav out)` contract assumes single-speaker monologue prompts; benching TTSD against single-speaker models would compare apples to oranges. Closer fit: a Dia-style "dialogue bench" track once one exists.
  - **MOSS-VoiceGenerator** is a *voice design* model — generates voices from text prompts without any reference speech. Task shape is "describe a voice → produce a speaker embedding/wav", orthogonal to either predefined or cloning TTS.
  - **MOSS-SoundEffect** generates sound effects, not speech. Out of scope for a TTS bench.
  All three deferred until a separate task-shape track exists for each.

_Implemented & live (no longer queued):_ **[Zonos2](https://github.com/Zyphra/ZONOS2)** (Zyphra, Apache-2.0, `Zyphra/ZONOS2`, 44.1 kHz) — added as `zonos2` and **benched + scored + published from the Linux-3090 on 2026-07-21** (cloning board / `kind=cloning`; pure zero-shot cloner, in `NO_PRESET_VOICE`; en/de/zh, `multilingual=False`). Sparse MoE ~900M active / 8B total; successor to `zonos` (v0.1), which it supersedes. **Linux-only, Windows-incapable** — `uv sync` builds a compiled sgl-kernel/flashinfer stack and `TTSLLM` spins up an internal sglang-style engine (paged KV cache sized to fill VRAM → grabs ~21 GB, reports whole-GPU `peak_vram_mb` like vLLM/Orpheus), so Linux owns the whole pipeline (Win/Mac show fail rows). **Speed:** warm RTFx ~2.0–2.1× (rises with clip length), cold TTFA 2.5–8.3 s. **Scores:** UTMOS 4.282 / WER 0.082 / **SIM 0.355 — quality (UTMOS) is strong but speaker-similarity to the Chris ref is low, well below the top cloners (echo 0.86 / indextts 0.82)**. Three runner gotchas caught on first execution (all fixed, see `runners/zonos2_runner.py` VERIFIED header): (1) `generate_one()` returns audio as raw PCM float32 **bytes**, not a tensor — the draft length calc undercounted `audio_s` to ~1 sample (RTFx ~0); (2) default `max_tokens=1024` truncated the long paragraph at ~11.9 s mid-sentence (in-process path doesn't auto-raise to the model limit like the server) — pass `resolve_max_tokens()`; (3) with that lifted the default `memory_ratio=0.9` left only ~2.1 GB free → DAC vocoder OOM on the full clip — `memory_ratio=0.8`.

_Implemented & live (no longer queued):_ **LFM2.5-Audio-1.5B** — added to the harness as `lfm2_audio` and **published to the default board 2026-06-22** (predefined-voice / `kind=predefined`; its TTS mode offers 4 preset voices, verified no cloning; 24 kHz; English-only; single-process `pip install liquid-audio`, cross-rig cpu+cuda). See `runners/lfm2_audio_runner.py` + `docs/known-issues.md`.

_Implemented & live (no longer queued):_ **MioTTS 0.1B + 0.6B** — added to the harness as `miotts_01b` / `miotts_06b` (server-backed: a llama.cpp/Ollama LLM emits MioCodec tokens → the MioTTS REST server decodes to 44.1 kHz wav; thin HTTP-client runner `runners/miotts_runner.py` à la `higgs_v3`). **Benched + full-published + scored from the Linux-3090 on 2026-06-23** (cloning board / `kind=cloning` — pure zero-shot cloner, in `NO_PRESET_VOICE`; EN/JA, English first-class). Scores: **0.1B** clean (UTMOS 3.6–4.4, WER ≤0.18, SIM ~0.36–0.38); **0.6B** mostly good but **p1 cold over-generated to ~17 s on the short prompt → UTMOS 1.34 / WER 0.43 / SIM 0.26** — LLM-codec length instability, model-inherent (cf. cosyvoice p1), kept visible on purpose so the board reflects its real, sometimes-bad quality. Licenses: inference code MIT; 0.1B Falcon-LLM, 0.6B Apache-2.0. See `runners/miotts_runner.py` + `docs/known-issues.md`.

- **[Gepard 1.0](https://huggingface.co/nineninesix/gepard-1.0)** (nineninesix.ai, 555.7M — Qwen3.5 14-layer backbone + NVIDIA NeMo NanoCodec, Apache-2.0). Skipped 2026-08-04. Licensing is fine (Apache-2.0; the codec's NVIDIA Open Model License is the same one `magpie` already ships under), it fits every rig, and it has real traction (10.6k downloads/month). **Skipped on its own published numbers plus an install shape we can't run at full speed.** (1) **Speaker similarity is outside the field.** Its card's seed-tts-eval table reports **SIM 0.585** against VoxCPM2 0.867 / OmniVoice 0.848 / Qwen3-TTS 0.833 / Chatterbox 0.796 / Fish-S2 0.789 — 0.20 below the next-worst. For a zero-shot cloner that is the product, and it would land near the bottom of our cloning lens. WER 0.036 is also 2nd-worst in its own table. Two naturalness metrics disagreeing argues for less confidence, not more. (3) **The axis it actually wins, we can't measure.** It is a streaming-latency play, and the card states plainly that the real-time numbers come from the [gepard-vllm](https://github.com/nineninesix-ai/gepard-vllm) path while "the reference PyTorch runner… isn't tuned for throughput." vLLM is the wall that already sank Orpheus and Voxtral on Windows; the reference [gepard-inference](https://github.com/nineninesix-ai/gepard-inference) stack is an HTTP server + client (CUDA + Python 3.12), so it's also a bar-#3 question. We'd install the slow path and publish speed numbers that undersell the model on its only competitive axis — worse than not adding it. 22.05 kHz (bottom of the range, against the 48 kHz preference); EN/ES/PT/NL + 5 English accents. **Revisit** as a Linux-3090 server-backed row (the `higgs_v3` pattern) where the vLLM path is real, or if a streaming/TTFA lens is added to the board.

- **[Breeze TTS 2](https://huggingface.co/BreezeBlue/Breeze-TTS-2)** (BreezeBlue / RESONIA, INC., 3.466B, released 2026-08-25). **Installed, runs, held from publish 2026-08-25.** Not MediaTek's Breeze/BreezyVoice — unrelated org, pure name collision (the MediaTek family is Traditional-Chinese ASR/LLM; note this in any display name). CSM-shaped: Qwen3 `llama-1B`-flavor backbone + `llama-100M` depth decoder, 16 codebooks over **kyutai/mimi @ 12.5 Hz → 24 kHz** out. Three modes: voice **clone** (ref wav + exact transcript), voice **design** (natural-language instruction, no ref), voice **direction** (ref + instruction), plus inline vocal events (`(laugh)` / `[笑]`). en+zh → `multilingual=False` (prompt 5 completes but French is not a supported language; "it produced audio" is not evidence of support). Code Apache-2.0 ([breezeblue-ai/breeze-tts](https://github.com/breezeblue-ai/breeze-tts), pinned `ca632ce`); weights under the BreezeBlue Research and Non-Commercial License.

  **Install passes cleanly, and it is NOT Linux-only.** Upstream's README says Linux, but nothing in the eager path requires it: `requirements.txt` is short and wheel-only (torch, torchaudio, `qwen-tts==0.1.1` (pure-python, Apache-2.0), `transformers==4.57.3` exact, soundfile, fastapi), **no vLLM and no flash-attn** — flash-attn lives only in the optional Docker image. Two gotchas, both fixed: (1) `load_runtime(device=...)` calls `torch.cuda.set_device`, so it needs an **indexed** `cuda:0`; bare `"cuda"` raises. (2) The real Windows blocker — the checkpoint pins `text_encoder_config.preferred_attn_implementation="flash_attention_2"` and `breeze.py` applies that to the T5Gemma2 text encoder **regardless of the top-level `attn_implementation="eager"`**, so loading dies with an ImportError for a package that has no Windows wheel. Fix: load `BreezeConfig`, set that field to `"sdpa"`, pass `config=` into `from_pretrained` — `t5gemma2_compat.py` dispatches non-flash impls through `ALL_ATTENTION_FUNCTIONS`, so sdpa is an equivalent substitute. **CUDA-only regardless of OS:** `FastBreezeStreamingRuntime.__init__` hard-raises `RuntimeError("fast streaming requires a CUDA device")` (`models/fast_streaming.py:192`) even with `fast_all=False`, so there is no CPU row to claim — `["cuda"]` only.

  **Measured (Win-5090, eager, bf16, canonical prompts).** 24 kHz confirmed. All prompts complete; cap is generous (`infer.py` uses `max_new_tokens=1500` = 120 s @12.5 fps; longest measured 221 frames ≈ 17.7 s, so even the `generation_config` default of 750 = 60 s would not truncate). Warm **RTFx ~0.46× (sub-realtime)**, TTFA ~365–460 ms warm / ~3.4 s cold. It genuinely streams (`iter_audio_chunks`), so TTFA is a real time-to-first-chunk, not a copy of `gen_s`. Three consecutive identical runs gave bit-stable `audio_s` (5.28 s ×3) — **no warm-state leak**; the `Residual tail decode detected` warning is an end-of-request notice, and `iter_audio_chunks` already does `open_request(reset=True)` + `close_request` in a `finally` (`fast_streaming.py:757,942`). A runner should still use a unique `request_id` per run and close the generator.

  **Why it is held — the lens has no clean home.** Cloning is genuinely strong: against `chris_hemsworth_15s.wav` the clone matches the reference at **ΔF0 2.3 Hz / LTAS-cos 0.982**, better than most of the board. But the **no-reference path has no stable voice.** With the default instruction ("Speak clearly and naturally.") and a pinned seed, median F0 wanders **114.6 → 215.1 Hz across prompts 1–5** — a different speaker, sometimes a different apparent sex, per prompt. Pinning a *specific* Maya1-style description + `--cfg-scale 4` helps a lot and makes identity **seed-stable** (ΔF0 0.8–4.5 Hz across seeds), but across prompts it still drifts more than any shipped default row:

  | row | medF0 range across p1–p4 | max pairwise ΔF0 | LTAS-cos min / mean |
  | --- | --- | --- | --- |
  | `maya1` (the board's other voice-design row) | 97.5–106.3 Hz (8.8) | 8.8 Hz | 0.952 / 0.966 |
  | `kokoro` (true preset anchor) | 197.2–207.7 Hz (10.5) | 10.5 Hz | 0.973 / 0.982 |
  | `melotts` (loosest shipped preset) | 234.5–264.8 Hz (30.2) | 30.2 Hz | 0.867 / 0.932 |
  | **`breeze_tts2` (pinned instruction, cfg 4)** | **98.6–136.3 Hz (37.7)** | **37.7 Hz** | **0.781 / 0.867** |

  So it does not clear the Default board's bar even at its best, and `NO_PRESET_VOICE` (cloning board) is where it belongs on behaviour. **That is exactly the path the license closes.** §4 explicitly permits publishing "benchmark results, and illustrative samples … in … repositories, or non-monetized demonstrations" with acknowledgment — the redistribution bar passes. But **§5(c)/(d) prohibit using the model to "clone, simulate, imitate, or impersonate a real person's voice … without that person's explicit and legally sufficient consent"**, and prohibit submitting reference audio you lack rights to, **with no research carve-out** (unlike `higgs_v3`, whose license affirmatively blesses non-production benchmarking of exactly this kind). Since `NO_PRESET_VOICE` models publish a **house Chris clone as their default clip**, there is no cloning-board configuration that avoids the prohibited act. Two independent reviews (Codex, Grok) reached this reading separately.

  **The one shippable-today shape, if a row is wanted anyway: a `SPEED_ONLY` row.** Register it like `maya1` — `can_clone=False` with a pinned `DEFAULT_VOICE_DESC` — and `harness.py:376` skips the cloning lens outright, so **no reference audio is ever fed to the model and the §5(c) act never happens**. Then add it to `publish.py`'s `SPEED_ONLY` (mirrored in `arena/build_manifest.py`), which drops it from `_ok_models` → no Listen clips, no Scores row, no Arena vote — only the Speed hub, which reads CSV directly. That publishes the model on the one axis it is actually about (latency/RTF) while making no voice-quality claim the 37.7 Hz drift can't support. **Cost:** `can_clone=False` understates a model whose headline feature *is* cloning, and the row carries no audio a reader can check — so it is a defensible half-row, not the real one. Prefer it over a Default-board row; prefer the hold over both unless the speed number is wanted now.

  **Revisit when any one of these is true:** (a) the cloning lens moves to a consent-clean reference — a voice Tym owns or a demonstrably synthetic one — which would unblock this and every future model under a §5(c)-style license (note SIM is only comparable within one reference, so this means re-running the cloning board, not just Breeze); (b) a **streaming/TTFA lens** is added, which is this model's actual headline axis (the card *claims* <40 ms TTFA and 0.32 RTF on H100 with `--fast-all`, and separately claims #1 open-weight on the Artificial Analysis TTS Elo — none of that is independently verified here; our own measurement is 0.46× RTFx / ~365 ms warm TTFA eager on a 5090) and the one our current speed column understates — the `--fast-all` CUDA-graph/compile path is in-repo and installable, so unlike [Gepard](#) the fast row is measurable here, and the `audio8` base+fastpath pairing would apply; or (c) upstream relicenses. The venv, pinned clone and weights are already on Win-5090, so a green light is a runner + registries away, not a reinstall.

## Runtime / tooling references (not bench models — watch list)

These aren't models to add; they're native **C++/ggml runtimes** (a "llama.cpp for audio") that reimplement several models we already track. Relevance to the bench is narrow and singular: a future **native-backend speed ceiling** for the Speed lens (the same weights running Nx faster than the Python reference path we currently time), and a possible way to cut per-model Python-env install pain. They do **not** add new models and do **not** change quality scores (same weights, no quant by default), so adopting one is a methodology call, not a new row. Both are also early/solo-maintained on a forked ggml. Revisit when streaming + a real server + stable CUDA land. Logged 2026-06-26 from an r/LocalLLaMA thread.

- **[audio.cpp](https://github.com/0xShug0/audio.cpp)** (0xShug0) — **TTS-first**. 12 of 25 model families released, overlapping our `pocket`, `chatterbox`, `omnivoice`, `voxcpm`, `qwentts`, `miotts`. Claims 3–5× vs the Python reference path on CUDA (no-quant fp16/fp32; warm-session RTFx up to ~48× real time on PocketTTS long-form). Caveats: no framework-wide streaming (offline only), self-described "naive" server, GGUF support pending, CPU barely optimized (author is CUDA-focused), and Windows French PocketTTS is broken (24-layer flow mismatch). Built clean-slate around a uniform module abstraction (every op, even ADD, is a metadata-carrying module) for a planned future feature.
- **[CrispASR](https://github.com/CrispStrobe/CrispASR)** (CrispStrobe, 349★) — **ASR-first** (Parakeet TDT, Canary 1B v2, Voxtral, Cohere Transcribe + universal forced alignment) but also does TTS (Qwen3-TTS, Orpheus, **IndexTTS**). **GGUF-native** and far more mature: WASM/iOS/Android/Flutter/Go/Python bindings, HF Space demo, Docker CUDA+Vulkan, AMD/HIP, ~71 runtimes. Overlaps our `indextts` (the by-ear cloning pick) + `qwentts`. The more deployment-ready of the two; the audio.cpp author started fresh rather than contribute here specifically to avoid retrofitting his module abstraction onto CrispASR's pragmatic structure.

- **[Audio8 TTS Preview 0.1B](https://huggingface.co/Audio8/Audio8-TTS-Preview-0.1b)** (Audio8,
  ~170M excluding the ~120M codec decoder, 44.1 kHz, 11 languages incl. French, zero-shot cloning
  **and** real `<|speaker:N|>` presets). **Added 2026-08-27.** The link came in via
  [r/LovingOpenSourceAI](https://www.reddit.com/r/LovingOpenSourceAI/comments/1vzw0hw/) pointing at
  the [ONNX INT8 build](https://huggingface.co/Audio8/audio8-TTS-0.1B-ONNX-INT8); the row we added is
  the **PyTorch base checkpoint behind it**. Timeline is why this was never triaged before: we added
  the 0.6B pair on 2026-08-04, the 0.1B base landed **2026-08-19**, the ONNX build **2026-08-25**.
  **It is not a shrunk 0.6B.** Its slow AR is a **Falcon-H1 hybrid (attention + Mamba)** where the
  0.6B's is plain attention, so `audio8` vs `audio8_01b` is a size+architecture pairing, distinct
  from the `audio8` vs `audio8_fast` engine pairing already on the board. Shares the venv and runner
  (`--variant base_01b`); Falcon-H1 ships inside the pinned transformers 4.57.5, so no extra install.
  **Smoke findings (Win-5090, 2026-08-27):** canonical prompt 3 completes at 16.95 s (~365 frames,
  well inside the 1024-frame cap); four speaker tags produce genuinely distinct voices (F0 144.6 /
  148.5 / 159.8 / 173.6 Hz, 29 Hz spread, differing spectral centroids) so it is
  `_PRESET_AND_CLONE`, **not** `NO_PRESET_VOICE`, and fills both lenses; generation is deterministic
  under a pinned seed; cloning tracks the reference (clone 132.4 Hz vs reference 137.8 Hz).
  **Two traps recorded in `docs/known-issues.md`:** (1) the licence **diverges from its 0.6B
  sibling** — the 0.6B is Apache-2.0, the 0.1B is the revenue-capped `Audio8 Community License
  v1.0`, so do not copy the sibling's registry row; (2) without `mamba-ssm` + `causal-conv1d`
  (no Windows wheels) transformers runs the naive Mamba path, making the 0.1B **slower than the
  3.5x larger 0.6B** on this rig — a floor, not the model's ceiling.
  **Note for the ONNX follow-up:** the ONNX repo self-tags `apache-2.0` while its declared
  `base_model` is the community-licensed 0.1B. That inconsistency is upstream's, and it should be
  resolved (or the stricter licence assumed) before an `audio8_01b_onnx` row is added. That row is
  otherwise attractive — it would be the board's only **torch-free CPU zero-shot cloner**, where
  every current CPU-only row (`kittentts`, `scyllasband`, `supertonic`, `piper`) is preset-only —
  but its inference code lives in the
  [GitHub repo](https://github.com/Audio8-AI/Audio8_TTS/tree/master/onnx_runtime), not the HF repo,
  so it needs its own venv and runner rather than a variant flag.
