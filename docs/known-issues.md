# Known issues

Frictions surfaced while building the harness. None are blockers on Mac/Linux — most apply to Windows or to specific models.

## Cross-cutting

- **`uv venv` doesn't seed pip.** `python -m pip install ...` fails inside a fresh uv venv. Installs use `uv pip install --python <venv-python>` throughout. The install scripts codify this.
- **PowerShell 5.1 + native exes + `$ErrorActionPreference=Stop` is a trap.** `uv` prints to stderr on success (`"Using CPython 3.11.15"`); PowerShell wraps each stderr line as a `NativeCommandError` and trips Stop even on exit 0. `install.ps1` uses `$LASTEXITCODE` checks instead.

## Per-model

- **Scylla's Band — the ten voices differ by 0.53 UTMOS, and the namesake voice is not the best one.** The bundle manifest lists all ten as peers (one style each, all four languages each, no quality or "recommended" field), so there is no in-band signal for which to bench. Measured over the 4 English canonical prompts (`scoring/voice_sweep.py`, Linux, UTMOS + WER): **`ink` 4.348** > tuesday 4.282 > felix 4.252 > orpheus 4.239 > **`scylla` 4.235** > ariadne 4.143 > stone 4.120 > gwen 4.083 > rex 3.989 > max 3.822. That 0.526 spread is wider than the gap between the board's median (~4.05) and its top-8 cutoff (~4.34) — the voice choice moves this model several places on the leaderboard, so it is not an arbitrary pick. **`ink` is the benched default.** Two traps worth naming: (1) `scylla` is the project's *namesake* and the voice in upstream's quick-start, which makes it the intuitive default — it placed **5th, with the 2nd-worst WER (0.1174)**; the name carries no quality meaning. (2) `ink`/`orpheus`/`tuesday` declare `en_gb` as their manifest `default_language`, but rendering them at en_gb makes all three *worse* (ink 4.348→4.205, orpheus 4.239→4.213, tuesday 4.282→4.075). Since all three moved the same direction, that is more likely UTMOS's en_US training bias than genuine degradation — but either way the benched figure is **ink-at-en_us**, which is what the harness's `en → en_us` mapping produces. WER across the ten spans 0.075–0.120 and quantizes hard at n=4 prompts, so treat it as an outlier detector, not a ranking.
- **Scylla's Band — the six affect axes are effectively inert at the default `affect_guidance_scale` of 1.0; you need g≥3 to hear anything.** The emotion control is the model's only real differentiator over other small fixed-voice engines, and at upstream's default it does almost nothing: same voice, same text, `joy=0.75` at g=1 moves mean f0 by **+3 Hz** (182.5 → 185.7) and is inaudible in an A/B. At g=3 it becomes obvious, and the strongest effect is on **duration**, not pitch — `sadness=1.0 g=3` stretches a line to 4.32 s while `anger=1.0 g=3` compresses the same line to 3.40 s, a ~40% swing; `anger=1.0 g=6` lifts f0 by 82 Hz (182 → 265) and raises RMS. This is the documented CFG behavior (the model was trained with 0.15 affect-condition dropout), but anyone evaluating at defaults will reasonably conclude the emotion control is fake — we did, on the first listening pass. The bench's default lens deliberately renders **neutral with no affect set**, so the board shows the model's plain delivery; the affect axes are a feature to reach for, not something baked into the benched clips.
- **Scylla's Band — the single-shot `synthesize()` API cannot render long text; the runner uses `synthesize_stream()`.** The ONNX bundle ships fixed-size graph exports bucketed at 256/384/512/640 latent frames, and anything predicted above 640 raises `ValueError: Predicted 670 latent frames, but this bundle supports at most 640` (the message says "LiteRT bundle" even on the ONNX path — upstream cosmetic bug). Canonical bench prompt 3 predicts 670–705 frames and failed on **every voice**. `synthesize_stream()` is the long-form path: it plans the text into chunks (2 for prompt 3), renders each inside the cap, and emits `audio_chunk` events the runner concatenates. Side benefit: `ttfa_ms` is a real time-to-first-chunk (~2.1 s on prompt 3 vs 3.3 s total) instead of equalling `gen_s`. Note that RTFx *rises* with clip length here, opposite to the usual intuition: benched warm on the 9950X3D it is **4.7× on prompt 1** (2.53 s of audio) but **8.0× on prompt 3** (14.29 s). Fitting the warm runs gives roughly a **0.27 s fixed cost per call plus a ~9.4× marginal rate**, so short lines simply have less audio to amortize the per-call overhead over. Don't quote in-process loop figures for this model — those omit the per-call setup and read ~13–17×, well above what the bench measures.
- **Miso TTS 8B — cloning is unstable shot-to-shot (benched at cooler sampling), and output texture is artifact-prone in BOTH modes.** At upstream sampling defaults (temperature 0.9 / topk 50) the clone usually loses the reference voice entirely — the by-ear A/B (2026-06-10, chris reference) failed at 0.9/50 and held the voice at 0.7/30 and 0.5/20, with one 0.7/30 generation still drifting. The runner benches cloning at **temp 0.7 / topk 30** (default-voice mode keeps upstream sampling), but voice retention remains stochastic per generation — flagged `⟳ clone unstable` (warn) on the Listen gallery; per-clip SIM against the reference ranges **0.03–0.74**. Separately, by-ear QA hears **audible artifacts/glitches in both modes** — the default voice *character* is good but the texture is rough — flagged `⚠ artifacts` (warn) on the default lens. The objective scores agree: UTMOS ~3.9 (bottom half) and mean WER ~0.42 (3rd worst; long prompts sometimes run on to the 30 s generation cap). Caveat: both rigs run our torch 2.7.1 + torchtune 0.6.1 stack in place of upstream's pinned torch 2.4.0 + torchtune 0.4.0 (pre-Blackwell), so a stack contribution to the artifacts isn't ruled out — the hosted demo at misolabs.ai is the stack-independent reference.
- **LongCat-AudioDiT — the 1B is the better clone; the 3.5B is less reliable despite being the bigger model, and both have a sampled (non-fixed) default voice.** This Wav-VAE + DiT diffusion model clones well at the small size — **1B** holds the reference voice consistently (Seed-style SIM ~0.87 mean, top-of-board) and is the recommended LongCat variant for cloning. The **3.5B** is weaker shot-to-shot: by-ear A/B (2026-06-14, chris reference) and SIM agree that it can lose the reference voice on a generation (p1 SIM 0.63 vs the rest ~0.90) and carries the same texture issues the larger model doesn't fix — flagged `⟳ clone less reliable` (warn) on the 3.5B cloning row. In **default** mode (no reference) both sizes sample a fresh voice from the diffusion prior, so each prompt's default clip is a *different speaker* — flagged `⟳ voice varies` (neutral) on both default rows; the consistent voice is the cloning lens. CUDA-only (DiT + fp16 Wav-VAE), 24 kHz, ZH + EN (French prompt skipped). Runs the upstream APG (adaptive projection guidance) path at NFE 16.
- **OmniVoice MPS — long-prompt "OOM" was a spurious MPS-watermark trip (FIXED for default voice).** The 30-word Parakeet paragraph (prompt 3) failed with "MPS backend out of memory (MPS allocated: 3.38 GiB, other allocations: 16.73 GiB)" on a 16 GB M4 — but the allocator was over-counting unified-memory "other allocations": real usage is only ~1.1 GB. **Fix:** `omnivoice_runner.py` sets `PYTORCH_MPS_HIGH_WATERMARK_RATIO=0.0` (disabling the early-OOM ceiling) before importing torch on the mps device; the long-form default-voice cell now completes at ~0.4–0.7× RTFx. **Cloning** (with the canonical `chris_hemsworth_15s.wav` reference) also benefits from the same watermark fix: mps now passes **4/5 prompts** — only the 30-word long-form (prompt 3) genuinely pushes past 16 GB and is OS-killed (SIGKILL); cpu does the full **5/5**. Both are sub-realtime (~0.1–0.3× RTFx), so OmniVoice cloning on a 16 GB Mac works but is slow — prefer a CUDA rig for cloning throughput.
- **OmniVoice — tops the blind cloning vote on voice match, but intelligibility is its weak spot (don't read #1 as "best overall clone").** The pairwise study (`docs/cloning.md`) ranks OmniVoice #1 because listeners pick the better **voice/accent match** — and its timbre fidelity genuinely is top-tier. But that 2AFC doesn't measure intelligibility, and OmniVoice can **drop or garble words** (high WER), so a clip can win the A/B while being less usable than a lower-ranked, fully-intelligible clone. The README/`cloning.md` claims are qualified accordingly, and the objective **WER** column on the [Scores lens](https://5uck1ess.github.io/tts-bench/scores.html) exists to quantify exactly this — audition (or check WER) before relying on OmniVoice for anything where the words have to land.
- **VibeVoice 1.5B — not viable on a 16 GB Mac (GPU-class here).** With the reference wav present it *does* run on **cpu**, but at ~0.03–0.07× RTFx (67–87 s to generate 2–5 s of audio) and the long-form prompt times out at the 600 s cell limit; on **mps** it OOMs at load (`RuntimeError: Invalid buffer size: 10.94 GiB` — the 1.5B in float32 exceeds 16 GB). It is therefore tagged GPU-class (`harness.py`) and skipped on non-CUDA rigs by default (force with `bench.py --all`). It runs normally on the CUDA rigs. The 0.5B streaming variant (`vibevoice`) runs fine on both cpu and mps. For the 1.5B use CUDA or a 32 GB+ machine.
- **VibeVoice 1.5B — needs a local 15s reference wav for its default voice.** Unlike the 0.5B variant (which auto-downloads `.pt` voice presets to `~/.cache/vibevoice-voices/`), the 1.5B path ships no bundled voice and falls back to `reference/chris_hemsworth_15s.wav`. That file is gitignored and not shipped, so on a fresh machine the predefined-voice run fails with `FileNotFoundError: Voice reference wav not found`. Drop any ~15s wav at that path, or pass `--reference <wav>`.
- **MARS5 — sub-realtime on Apple Silicon CPU; times out in the bench.** mars5 (torch.hub) on M4 CPU exceeds the 600s per-cell bench timeout and records as `timeout 600s`. It has no MPS path (cpu/cuda only) and is slow even on CUDA (see Pending work in the README). Treat as unusable on Mac.
- **LuxTTS — blocked on Windows AND Apple Silicon.** Depends on `piper-phonemize` 1.1.0 which only ships wheels for `manylinux_2_28_{x86_64,aarch64}` and `macosx_10_14_x86_64` (Intel Mac only). On arm64 macOS (M-series) the install fails with "no wheels with a matching platform tag (e.g., `macosx_26_0_arm64`)". Workaround: build piper-phonemize from source (untested) or use Linux. The README previously claimed "should install cleanly on macOS — piper-phonemize macOS wheels exist" — that's only true for Intel Macs. Also note the cloned repo's pyproject lists `name = "Zipvoice"` even though the GitHub repo is named LuxTTS, so the runner imports `from zipvoice.luxvoice import LuxTTS`. (Piper proper is unaffected — `piper-tts` 1.4+ bundles espeak-ng and dropped the piper-phonemize dependency.)
- **NeuTTS — `pip install neutts` gives the torch backbone, not the production fast path.** Torch backbone on x86 CPU runs at ~0.2× RTFx (unusable). Production path is `llama-cpp-python` + `neuphonic/neutts-*-q4-gguf` models. Post-switch RTFx is what's in the table. Install scripts install the GGUF path by default.
- **NeuTTS — reference voices need both `.wav` AND `.txt` (transcript).** Wav-only fails inside `encode_reference()`. Pocket-TTS in contrast takes a voice name string or a single wav (gated).
- **NeuTTS Nano — multilingual = separate model file per language.** `neuphonic/neutts-nano-q4-gguf` (EN), `neuphonic/neutts-nano-french-q4-gguf` (FR), etc. Runner switches based on `--language`.
- **Pocket-TTS — voice cloning is HF accept-terms gated.** Predefined voices work without auth. Reference-wav cloning triggers a fetch of the gated `kyutai/pocket-tts` repo and 401s. Either accept terms or use NeuTTS Air/Nano for BYO-voice without auth.
- **Kokoro — misaki tokenizer calls `spacy.cli.download()` at init.** Tries to install `en_core_web_sm` via pip; fails in uv venvs. Install scripts pre-install the model wheel directly to bypass this.
- **Kokoro MLX (`kokoro_mlx`) — the MLX backend is SLOWER than PyTorch-MPS on Apple Silicon, so MPS stays the recommended Mac path.** Same Kokoro-82M weights + voices run through Apple's MLX (mlx-audio, `prince-canuma/Kokoro-82M`) instead of PyTorch's Metal (MPS) backend. Measured head-to-head on the M4 (16 GB), same 5 prompts, same warm protocol, in one `mac-default` run: **warm MLX is 0–6% slower than MPS and never faster** (RTFx — p1 13.74 vs 13.77×, p3 16.23 vs 16.31×, p4 14.94 vs 15.55×, p5-FR 14.63 vs 15.54×), and **cold start is ~3.5× worse** (first-call TTFA ~2057 ms vs ~595 ms — MLX pays a JIT kernel-compile cost that PyTorch doesn't). It's also **less robust**: mlx-audio crashes on prompt 2 (`ValueError: [broadcast_shapes] Shapes (1,140400,1) and (1,140700,9) cannot be broadcast` — the `I'll … pull request` contraction-heavy line), recorded as a failed cell. Kokoro-82M is small enough that PyTorch's Metal path is already well-tuned, so MLX's native-kernel advantage (real for larger LLM-class models) doesn't materialize. Published as a **speed-only** row so the M4 board shows MLX vs MPS side by side (`SPEED_ONLY` in `publish.py`/`arena/build_manifest.py` keeps it off Listen/Scores/Arena — the audio is identical to PyTorch Kokoro, which already publishes clips from a CUDA rig). Apple-Silicon only (mlx has no CUDA/Linux wheel); `install.sh` builds the `kokoro_mlx` venv on Darwin only and needs the same `misaki[en]` + `num2words` + `en_core_web_sm` wheel as `kokoro`.
- **KittenTTS — needs `espeakng-loader` (bundles espeak-ng DLL).** System espeak install also works on Mac/Linux but is more friction. Runner sets `ESPEAK_DATA_PATH` env var because the bundled DLL has a hardcoded CI build path.
- **ChatterBox — needs `setuptools<80`.** The `perth` audio watermarker imports `pkg_resources` (removed in setuptools 80+). Install scripts pin the version.
- **F5-TTS — `torchaudio.load()` routes through `torchcodec` in torch 2.12+**, which needs FFmpeg shared DLLs (libtorchcodec_core4.dll etc., NOT just ffmpeg.exe). On Windows with the typical static FFmpeg build this fails. Runner monkey-patches `torchaudio.load` to use `soundfile` directly. Install scripts also pin `datasets<3.0` to avoid pulling torchcodec into the import chain.
- **Fish Speech 1.5 — two Apple-Silicon install gotchas (both fixed in `install.sh`).** (1) **portaudio:** the editable `fish-speech` install pulls `pyaudio`, which compiles against `portaudio.h`. macOS ships none, so the build dies with `'portaudio.h' file not found`. Fix: `brew install portaudio`; `install.sh` now puts its `--prefix` `include`/`lib` on `CPATH`/`LIBRARY_PATH` (and warns if portaudio is missing). (2) **torch cu128 reinstall:** `install.sh` reinstalled torch from `--index-url .../whl/cu128` as its last step, but that index ships **no macOS-arm64 wheel** — uv resolves "unsatisfiable" (`no wheels with a matching platform tag, e.g. macosx_*_arm64`) and the install aborts. Fix: the cu128 reinstall is now Darwin-guarded (Mac keeps the default torch the editable install already pulled), matching styletts2/zonos/openvoice. Post-fix, fish_15 benches on Mac but is sub-realtime (cpu ~0.34×, mps ~0.31× RTFx — it's a GPU-class model here).
- **VibeVoice — install from `vibevoice-community/VibeVoice`, NOT pypi or `microsoft/VibeVoice`.** pypi `vibevoice==0.0.1` only ships the base architecture (no streaming class). The official Microsoft repo was taken down in September 2025 then partially restored without code. The community fork at github.com/vibevoice-community/VibeVoice keeps the original code and added a working streaming variant on 2025-12-04. Voice presets (`.pt` files, 2-4MB each) are not bundled in the package — runner auto-downloads them from the fork to `~/.cache/vibevoice-voices/` on first use.
- **VibeVoice — the "you should probably TRAIN this model" warning is benign.** The HF checkpoint deliberately omits the `acoustic_tokenizer.encoder` weights (~400 keys load as random). That subnet is unused at inference because the `.pt` voice presets are pre-encoded representations. Audio output is unaffected.
- **ZipVoice — needs `torchcodec` + FFmpeg shared libs to load the reference wav.** The venv's torch 2.11+ routes `torchaudio` audio loading through `torchcodec`; without it, reference loading fails with `ImportError: TorchCodec is required for load_with_torchcodec`. Install scripts add `torchcodec`, and `zipvoice_runner.py` discovers the FFmpeg lib dir and re-execs once with it on `LD_LIBRARY_PATH`, so a non-standard FFmpeg (e.g. linuxbrew, whose libs aren't on the default loader path) is found. torchcodec supports FFmpeg 4–8. Windows needs the "full-shared" FFmpeg build (ships DLLs); alternatively pin torch<2.9 to skip torchcodec. (F5-TTS dodges the same issue differently — it monkey-patches `torchaudio.load` to use `soundfile`.)
- **ZipVoice — CUDA OOMs on ≤24 GB GPUs (k2 not installed).** k2 is intentionally skipped (no wheels for the venv's torch/CUDA combo), so the Swoosh ops fall back to a memory-hungry PyTorch path that allocates >24 GB of VRAM and OOMs even on short prompts (e.g. an RTX 3090 fails on a 20 MiB request because the process already holds ~23.5 GB). CPU works fine — the same path uses ~30 GB RAM. Use CPU on ≤24 GB rigs; a 32 GB+ card (e.g. RTX 5090) fits it.
- **MOSS-TTS-Nano (100M) — works everywhere; MOSS-TTS flagship (8B, v1.0 + v1.5) runs on the Linux-3090.** The Nano variant installs and runs fine (CPU + CUDA). **Install gotcha:** the 8B's `[torch-runtime]` extra is installed with `--extra-index-url cu128`, and uv's default `first-index` strategy then finds `tqdm` on the cu128 torch index but not the pinned `tqdm==4.67.1` (which is on PyPI), and won't fall back, so the solve fails. Adding `--index-strategy unsafe-best-match` lets it resolve `tqdm` from PyPI while torch comes from cu128. **VRAM — fits after all (note corrected 2026-06-08):** an earlier note claimed the 8B Qwen3-backbone wouldn't fit the 3090's 24 GB, but both `moss_tts` (v1.0) and `moss_tts_v15` (v1.5) bench cleanly on the 3090 (bf16 weights ~16 GB; v1.5 runs at 0.9–2.3× RTFx — faster than realtime). Both are benched/published from Linux. v1.5 needs an explicit `language=` per prompt (with it omitted v1.5 can mis-route language); the runner passes it.
- **Zonos — `--device cpu` crashes on a CUDA-equipped host (fixed in the runner).** Zonos computes `DEFAULT_DEVICE = get_device()` at *import* time (`zonos/utils.py`), and `get_device()` returns `cuda` whenever any GPU is visible. Its conditioning helpers (`make_cond_dict`, `prepare_conditioning`) default new tensors to `DEFAULT_DEVICE`, so even when the model is loaded with `device="cpu"` the conditioning tensors land on `cuda:0` and `generate()` dies with `RuntimeError: Expected all tensors to be on the same device ... mat1 is on cuda:0 ... other tensors on cpu` (a `wrapper_CUDA_addmm`). It only bites CUDA rigs (Windows/Linux) — on a CPU-only box like a Mac, `get_device()` already returns cpu, which is why the cpu path works there. Fix: `zonos_runner.py` sets `CUDA_VISIBLE_DEVICES=-1` before importing torch/zonos when `--device cpu`, so `get_device()` (and therefore `DEFAULT_DEVICE`) resolves to cpu. Use `-1`, **not** `""` — an empty string is treated as *unset* and leaves all GPUs visible (the cpu cell then still failed with the same `cuda:0` error before the value was corrected).
- **Qwen3-TTS CUDA-graph (`qwentts_fast`) — cloning runaway (FIXED).** The fast engine's default text-feeding (`non_streaming_mode=False`, step-by-step during the CUDA-graph decode) never emits EOS for some longer prompts, so generation ran away to `max_new_tokens` (~147 s of garbled/looping audio; prompts 2–5 hit it stochastically). Default voice was unaffected. **Fix:** the runner now passes `non_streaming_mode=True` (prefill the full target text before decode) — it terminates correctly *and* is ~5–30× faster (gen_s ~1 s vs up to 38 s). Re-benched; durations are now sane (p2: 147 s → 4.3 s).
- **Qwen3-TTS Base (both sizes) — cloning is unusable: intermittent decode runaway, and `non_streaming_mode=True` does NOT fix it on the stock path.** Measured on 0.6B-Base via the stock `qwen-tts` package (5090, bf16, canonical prompt 3 + the 15 s Chris reference): decode intermittently fails to emit EOS and runs away to `max_new_tokens`, producing **655.3 s of audio from a ~13 s line** — the same input yielded 12.9 s on one call and 655.3 s on the next. It is **not a speed problem**: throughput holds a steady ~0.5–0.6× RTFx in both the good and the runaway runs, so the tell is `audio_s`, not `gen_s` (a timing-only check reads this as "slow model" and misses it). Passing `non_streaming_mode=True` — the fix that works for `qwentts_fast` above — reduces but does not eliminate it: 1 of 4 runs still ran away to the identical 655.3 s ceiling. **Scope correction to the `qwentts_fast` entry above:** that note attributes the runaway to the *CUDA-graph* decode; this reproduces with no CUDA graphs anywhere, so the defect belongs to the streaming text-feeding path in general — the prefill flag just happens to mask it under CUDA graphs. Consequence: both Base rows (`qwentts`, `qwentts_06b`) keep the cloning **lens** disabled; their default-lens Chris clone is what publishes, on the cloning board. All three Base rows (`qwentts`, `qwentts_06b`, `qwentts_fast`) are reference-only → `NO_PRESET_VOICE`. **Their fallback reference was `jo.wav`, not the house `chris_hemsworth_15s.wav`** (a deviation shared with `f5tts`/`indextts`/`step_editx`, and the same class of bug that made `fish_s2` clone jo instead of Chris) — corrected 2026-07-29, so the existing Qwen default-lens clips need a re-bench. `qwentts_06b_custom` is the only Qwen row with real preset timbres and stays on the Default board. The runner keeps `--variant base_06b`, so this is re-testable by invoking `runners/qwentts_runner.py` directly if upstream changes its EOS handling.
- **House-reference audit (2026-07-29) — five runners fell back to `jo.wav`/`juliette.wav` instead of the house `chris_hemsworth_15s.wav`.** The convention is that a model with **no preset voice is reference-only**: its no-`--reference` run clones the house Chris clip, and that clip is what shows on the Cloning board (`build_manifest.scan_dirs` pulls from the `*-default` dirs for `NO_PRESET_VOICE` models). Five runners deviated — `f5tts`, `fish_s2`, `indextts`, `step_editx`, `qwentts`/`qwentts_fast` — so their "default" sample was a **jo/juliette clone**, and three of them (`f5tts`, `indextts`, `step_editx`) were additionally *not* in `NO_PRESET_VOICE`, meaning they sat on the **Default board being voted on as if jo were their own voice**. This is the same defect that made `fish_s2` clone jo instead of Chris (entry below). **Fixed:** all four switched to `chris_hemsworth_15s.wav` and the three added to `NO_PRESET_VOICE` in both `publish.py` and `arena/build_manifest.py`. **All affected default-lens clips need a re-bench.** **`mars5` is the deliberate exception and must stay on `juliette.wav`:** MARS5 caps reference audio at 1–12 s, and both Chris clips (15 s / 67 s) and `jo.wav` (13 s) exceed it; juliette is 8.1 s. Giving mars5 a house-consistent reference would need a new short Chris clip (~8 s). Also fixed in the same pass: **`dots_tts` was in `arena/build_manifest.py`'s `NO_PRESET_VOICE` but not `publish.py`'s** — it has a real (per-prompt varying) default voice, so the arena was wrongly dropping it from the default lens. The two sets are mirrors and must stay in sync.
- **`qwentts` (1.7B Base, stock runtime) has no publishable clip set -- held in `SPEED_ONLY` (2026-07-29).** Once the default-lens fallback moved to the house Chris reference, the default lens became a clone too -- so it hits the same decode runaway that already forced `can_clone=False`. A re-bench on 2026-07-29 (`--models qwentts --devices cpu,cuda`, default lens) completed **prompt 1 only** (audio_s 1.6-2.2 s on both devices), then **prompt 2 hit the 600 s cell timeout on cpu AND cuda**, and p3-p5 were skipped. A longer timeout does not help: a runaway emits ~655 s of audio for a ~13 s line, so it would produce a garbage clip rather than a usable one. Its only complete clip set is therefore the **pre-fix jo clone (wrong voice)**, so `qwentts` is held out of Listen/Scores/Arena and keeps only its speed row. It stays in `NO_PRESET_VOICE` as well -- that records what the model *is* (reference-only); `SPEED_ONLY` records what we can *publish*. `qwentts_fast` is the same checkpoint on the CUDA-graph runtime and remains fully published, so the checkpoint is still represented. **Remove from `SPEED_ONLY` once the runaway is fixed.** Note the earlier `f48ca1c` had excluded `qwentts` for a different (and wrong) reason; this exclusion is measured, not assumed.
- **`qwentts_06b` (0.6B Base) fails the same way as the 1.7B Base -- also held in `SPEED_ONLY` (2026-07-29).** Benched on Windows to settle whether it was worth Linux's time: **cpu timed out on prompt 1** (so there is no cpu data at all), and **cuda cleared p1+p2 then timed out on p3** (p4-p5 skipped). Worse than a pure timeout -- the runs that *did* finish emit truncated audio: p1 produced **0.96 s / 0.48 s / 5.84 s across three runs of the same sentence**, and half a second cannot contain "Open the browser and read my email." So the stock `qwen-tts` path is broken for this checkpoint, not merely slow. The run was **never merged into a canonical**, so no partial cuda-only timings or truncated clips can surface. `qwentts_06b_custom` (0.6B CustomVoice, predefined timbres) is unaffected -- it benched 30/30 ok on the same box with sane audio (2.88-21.04 s) and is fully published. **Remove from `SPEED_ONLY` once the runaway is fixed.**
- **House-reference audit, follow-up pass (2026-07-29) — three more runners missed by the first sweep: `neutts_air`, `neutts_nano`, `luxtts`.** The first pass grepped for the literal `jo.wav`, but these three stored the fallback as a bare **stem** in a dict (`DEFAULT_REFERENCE = {"en": "jo", "fr": "juliette"}`) and appended the extension later, so the grep never matched them. All three are pure cloners that cannot speak without a reference — LuxTTS requires `encode_prompt(ref_wav)`, NeuTTS requires a wav + sibling transcript — yet none was in `NO_PRESET_VOICE`, so all three sat on the **Default board with a jo/juliette clone presented as their own voice**. **Fixed:** all three now use `chris_hemsworth_15s` (the `.txt` transcript NeuTTS needs already ships) and were added to `NO_PRESET_VOICE` in both files. This also removed a latent bug: `neutts_nano` supports de/es, which had **no** entry in the old per-language dict and hard-errored on a default-voice run. **Lesson: audit by reading each runner's reference resolution, not by grepping for a filename — the bug hides behind any indirection.** Two deliberate exceptions remain and are the ONLY non-house defaults: `mars5` (`juliette.wav`, 12 s cap) and `metavoice` (`chris_hemsworth.wav`, needs >= 30 s).
- **Fish Speech S2-Pro — cloning run used the wrong reference (a bundled default voice, not Chris).** The `fish_s2` runner's no-`--reference` default is `reference/jo.wav` (`{"en": "jo.wav", "fr": "juliette.wav"}`). On the Linux-3090 cloning pass it didn't receive a usable `--reference` and fell back to that default — so the cloning sample imitates jo/juliette, not the `chris_hemsworth` target every other model used. (`step_editx` shares the same default but cloned Chris correctly on this pass, and `metavoice` defaults to the 67 s `chris_hemsworth.wav`, so both of those are fine — only `fish_s2` needs fixing.) **Fixed:** re-benched on Linux with `--reference reference/chris_hemsworth_15s.wav` and `merge.py --replace`d into `linux-cloning`; it now clones Chris like every other model.
- **Higgs Audio v3 TTS — the bench's first SERVER-BACKED model; Linux + CUDA only, needs a Docker server running before you bench it.** v3 (`bosonai/higgs-audio-v3-tts-4b`, ~4B, `higgs_multimodal_qwen3`) ships only `config.json` + `tokenizer.*` + `model.safetensors` — no `modeling_*.py`, no `auto_map` — and the class isn't in stock transformers, so there's no single-process Python load (raw `.generate()` would emit audio *tokens* that still need the Higgs tokenizer decoder, wired only by SGLang-Omni). The supported path is a Docker container running `sgl-omni serve` exposing OpenAI-style HTTP `/v1/audio/speech`; `runners/higgs_v3_runner.py` is a thin HTTP client (venv = `requests`+`soundfile`+`numpy`, **no torch**). Standup: `docker pull lmsysorg/sglang-omni:dev`, then `docker run … --gpus all -v "$(pwd)":"$(pwd)" -w "$(pwd)" -e HF_TOKEN=hf_… lmsysorg/sglang-omni:dev`, inside it `uv pip install -e .` the cloned `sglang-omni`, accept the HF terms, and `sgl-omni serve --model-path bosonai/higgs-audio-v3-tts-4b --port 8000` (full recipe in `install.sh`'s higgs_v3 stanza). Gotchas: (1) the bench's normal cuda probe imports torch *in the venv*, which this venv lacks — the harness special-cases server-backed models (`SERVER_BACKED` set) to probe the GPU via `nvidia-smi` instead, so the cuda cell builds on a CUDA rig and is skipped (gpu-class) on non-CUDA rigs. (2) Cloning passes the reference by file path (`references[].audio_path`); the `-v "$(pwd)":"$(pwd)"` bind-mount makes the repo's real path valid inside the container so the absolute path resolves (a base64 inline form is preferred if a future cookbook adds it — see `_REF_USE_BASE64`). (3) `peak_vram_mb` is `None` (the model lives in the container, not the runner process); a coarse whole-GPU `gpu_used_mb` is reported via `nvidia-smi` but includes the whole server. (4) First pass is non-streaming, so `ttfa_ms == gen_s` (Higgs advertises sub-second TTFA via the streaming SSE endpoint — a later enhancement). 24 kHz, 100 languages.
- **Higgs Audio v3 — the default voice is sampled fresh each generation, so it's a different speaker per prompt.** With no `--reference`, the server's `voice="default"` draws a speaker from the model's voice prior, and the runner samples at `temperature=0.8`/`top_k=50`, so each of the 5 default-voice clips is a *different* identity (this is genuine synthesis, not a fallback Chris clone — so it stays in the Default-voice gallery, unlike the eleven no-default models below). **Cloning** (with `ref_audio`+`ref_text`) conditions on the reference and stays consistent across prompts. Surfaced as a ⚠ badge on its Default row in the Listen gallery. To pin one consistent default speaker, add a fixed `seed` to the runner's default-voice payload and re-bench the default pass.
- **MioTTS — SERVER-BACKED (the bench's second), Linux-only, needs TWO servers up before you bench it; reuses the box's llama.cpp.** MioTTS (`Aratako/MioTTS-*`) is an LLM-codec TTS: a small base LLM (GGUF) emits MioCodec tokens that a MioCodec torch model decodes to a **44.1 kHz** wav. Like higgs_v3 the runner loads no model — `runners/miotts_runner.py` is a thin HTTP client (venv = `requests`+`soundfile`+`numpy`, **no torch**, so it's in `SERVER_BACKED` → the harness probes the GPU via `nvidia-smi`, not a venv torch import). Standup (Linux + CUDA): (1) **LLM server** — reuse the box's `llama-server -hf Aratako/MioTTS-GGUF -hff MioTTS-0.6B-BF16.gguf --port 8000`; (2) **MioTTS REST orchestrator** — clone `Aratako/MioTTS-Inference` into `venvs/miotts/src`, `uv sync`, `python run_server.py --llm-base-url http://localhost:8000/v1 --port 8001` (downloads `MioCodec-25Hz-44.1kHz-v2` on first run). Full recipe in `install.sh`'s miotts stanza. Differences from higgs_v3 worth noting: (1) **cloning reference is base64 in-band** (`POST /v1/tts` `reference.type="base64"`) — **no Docker bind-mount and no sibling `.txt` transcript** (the win over higgs/cosyvoice); the pure-cloner default-lens path clones the house `chris_hemsworth_15s.wav`, so MioTTS is in `NO_PRESET_VOICE` (cloning board only). (2) **One GGUF per server session** — a single GPU hosts one GGUF at a time, so the two sizes (`miotts_01b`/`miotts_06b`, which share runner+venv+servers; `--variant` is labeling only) bench in **separate passes**: start the LLM server on the 0.6B GGUF, bench `miotts_06b`, restart it on the 0.1B GGUF, bench `miotts_01b`. (3) `peak_vram_mb` is `None` (model lives in the servers); coarse whole-GPU `gpu_used_mb` via `nvidia-smi`. (4) Non-streaming, so `ttfa_ms == gen_s`. Licenses: code MIT; 0.6B = Apache-2.0, 0.1B = Falcon-LLM. EN/JA.
- **DramaBox — CUDA-only (~18 GB VRAM), expressive *dialogue* TTS on an LTX-2.3 video-model backbone; short prompts get heavy silence padding (trimmed in the runner).** DramaBox (`ResembleAI/Dramabox`, 3.3B audio-only DiT, IC-LoRA fine-tune of LTX-2.3) is a source-clone install (no PyPI): the runner imports `src.inference_server.TTSServer` from `venvs/dramabox/src`, fetches the DiT + audio-components + a 4-bit Gemma-3-12B text encoder via the repo's `model_downloader` (~16 GB, HF-cached), and builds the server with explicit `checkpoint`/`full_checkpoint` paths + `compile_model=False` (the bare `TTSServer()` defaults to non-existent local `models/` files, and torch.compile/Triton is brittle on Windows). bitsandbytes (the 4-bit Gemma) *does* ship a working Windows wheel (0.49.2 on the 5090). Peak VRAM ~18 GB (audio-only mode frees LTX's video stack) → fits both the 5090 and the 3090. 48 kHz out (LTX "BWE" bandwidth-extension decode). Prompt grammar is `<speaker description>, "<dialogue>" <action>`; the runner wraps plain bench prompts in a neutral `A person speaks clearly, "…"`. Watermarked (Resemble Perth). **Gotcha:** DramaBox's duration estimator over-allocates for short lines, so a clip can open with several seconds of dead air — the runner trims leading/trailing silence (energy < −40 dB rel. peak, 0.1 s pad) so `audio_s`/RTFx aren't inflated. The optional RE-USE voice-ref denoiser (mamba-ssm) is skipped (no Windows wheel; off by default). Both lenses: no-reference = prompt-described voice (Default), 10 s+ wav = cloning.
- **dots.tts — CUDA-only 2B continuous AR TTS; the sampler MUST be seeded or it early-stops to a ~0.3s fragment.** dots.tts (`rednote-hilab/dots.tts`, Apache-2.0) is a pip package (`dots_tts`) source-clone editable install; the runner does `from dots_tts.runtime import DotsTtsRuntime` and `from_pretrained("rednote-hilab/dots.tts-soar", precision="bfloat16")` (the SCA flagship — best Seed-TTS-Eval quality; weights snapshot-download from HF on first run, ~5.3 GB VRAM at bf16, fits the 3090). **Gotcha:** the AR + flow-matching head hits an early end-of-audio if the RNG isn't seeded — an unseeded run emitted only 2 audio patches (15360 samples = 0.32 s) for a full sentence. The CLI/gradio both call `seed_everything()` before generating; the runner mirrors this (`seed_everything(42)` before each `generate`), after which "Open the browser and read my email." renders at the expected ~1.9 s. Sampler params follow the upstream **CLI** defaults (`guidance_scale=1.2`, `num_steps=10`, `speaker_scale=1.5` default) — NOT the README quick-start's `guidance_scale=1.0`, which is below the runtime default. Multilingual (24 langs incl. FR), 48 kHz. **Rig note — LINUX-ONLY.** The Windows install never worked — its `WeTextProcessing`→`pynini` dependency won't build under Windows MSVC (`cl` rejects pynini's GCC/Clang `-Wno-register` flag → `D8021`), and that import is hit at module load (`runtime.py` → `utils.text` → `tn`) so it can't be skipped — so dots.tts has **no `install.ps1` stanza** and is benched/published from the **Linux-3090** only. **Default voice — it has one, but it varies.** dots.tts *does* synthesize with no reference (it's not reference-only), but that own-voice is sampled fresh per prompt — a different speaker each generation, exactly like Higgs v3 — so it's NOT in `NO_PRESET_VOICE`; it shows in the Default-voice gallery with a "⟳ voice varies" badge, and under Cloning (consistent) when given a reference. Revisit `install.ps1` only if a working Windows path is found.
- **Zonos2 — Linux + CUDA only; pure zero-shot cloning through the in-process `TTSLLM.generate_one` API.** Zonos2 (`Zyphra/Zonos2`, Apache-2.0) supersedes Zonos v0.1 (`zonos`). It is an **8B sparse MoE (~900M active)** model with a **44.1 kHz** DAC output and no preset voice: `TTSLLM.embed_speaker_file()` embeds the reference and `TTSLLM.generate_one()` performs zero-shot cloning in-process. Upstream ships compiled CUDA kernels, so it has no CPU/MPS or Windows path and is installed only on the Linux-3090: git clone the source into `venvs/zonos2/src`, then `uv sync` it into the harness venv. It is therefore in every `NO_PRESET_VOICE` list and appears only under Cloning.
- **Twenty-one zero-shot models have no "default voice" — their no-`--reference` run clones the bundled reference.** `moss_tts`, `moss_tts_v15`, `moss_tts_nano`, `fish_15`, `fish_s2`, `metavoice`, `openvoice`, `zipvoice`, `zonos`, `zonos2`, `vibevoice_15b`, `vibevoice_7b`, `echo`, `qwentts`, `qwentts_06b`, `qwentts_fast`, `f5tts`, `indextts`, `step_editx`, `neutts_air`, `neutts_nano`, `luxtts` ship no preset/built-in speaker. With no `--reference` they fall back to `reference/chris_hemsworth_15s.wav`, so their "default voice" bench sample is just a (different, non-deterministic take of a) Chris clone — not a real default. The published Listen gallery therefore shows these models **only under Cloning**, never in the Default-voice section. Models that *do* ship a default — `styletts2` (bundled LibriVox speaker), `vibevoice` 0.5B (`en-Emma_woman` preset), ChatterBox, etc. — stay in Default normally.

- **Audio8 TTS — the compiled fastpath needs `triton-windows` on Windows, and its upstream `max_new_tokens=400` default silently truncates long prompts.** Two traps, both load-bearing. (1) **Triton.** `audio8_fast` runs the ScrappyLabs `fast_arktts` static-shape rewrite under `torch.compile(fullgraph=True, dynamic=False)`. PyPI `triton` is Linux-only, so on Windows the first attempt dies with `TritonMissing` and, if you fall back to `compile_mode=None`, you get **eager speed wearing the compiled label** (RTFx 0.71 — indistinguishable from the `audio8` base row). `uv pip install triton-windows` fixes it (3.7.1 against torch 2.11.0+cu128); this is the same wall that forced `compile_model=False` on DramaBox, and it *is* beatable. Linux needs no such wheel. (2) **The 400-frame cap.** `FastTTS` defaults to `max_new_tokens=400`, and because shapes are static that cap is baked into the compiled graph. The codec runs ~21.5 frames/s, so 400 frames is an **18.6 s ceiling** — and canonical bench prompt 3, cloned, measured **390 frames** on this rig. A ten-frame margin before silent truncation. The runner uses **1024** (~47 s). That does not slow generation (the loop still exits at EOS) but it does widen per-frame attention, so our RTFx is *conservative* against upstream's 400-frame figures. (3) **Compile cost is front-loaded, then cached.** First-ever `max-autotune` build is ~370 s; inductor caches to disk, so a fresh process afterward is ~50 s end-to-end. Compilation happens at load (`warmup=True`), i.e. outside the timed generate window — the same accounting as `qwentts_fast`'s CUDA-graph capture. Measured engine delta on the same weights (Win-5090): eager **0.71x** -> `default` compile **2.53x** -> `max-autotune` **15.06x**, a ~21x win versus upstream's advertised 5.8x (they benchmarked a 5090 *Laptop* at ~576 GB/s).

- **Audio8 TTS — clones English well and largely loses the voice in French; it tops the cloning board on naturalness while sitting mid-pack on speaker similarity.** Two separate findings from the Linux scoring pass, both easy to misread. (1) **The French cliff.** Per-prompt cloning SIM against the Chris reference: p2 **0.708**, p4 **0.704**, p3 **0.678**, p1 0.558 (short line, less material to match) — and canonical prompt 5, the French one, **0.363**. UTMOS drops with it (3.91 vs a 4.38 English mean). So the model reproduces a reference voice acceptably within English and mostly abandons it when asked to speak French in that voice. This is why `audio8`/`audio8_fast` are deliberately **not** in `report.py`'s `MODEL_CROSSLINGUAL` — that registry wants positive evidence of clone-in-one-language / speak-another, and here the evidence points the other way. Note the model is still legitimately `multilingual=True`: its *default-voice* French is fine, and the FR prompt runs. Cross-lingual **cloning** is the specific thing that fails. (2) **Naturalness and similarity disagree, and it matters which one you quote.** On English cloning prompts audio8 is **#1 of 43 on UTMOS** (4.382, with audio8_fast #2 at 4.373 — ahead of styletts2, higgs_v3, chatterbox) but only **#19/#20 of 43 on SIM** (0.665 / 0.655, against longcat_1b 0.870 / echo 0.836 / omnivoice 0.835). It produces the cleanest-sounding cloned audio on the board that doesn't especially sound like your reference. By-ear QA agreed on the pleasant part, which is exactly the trap — pick the metric that matches the question being asked. (3) **The compiled engine is not the cause of any of this.** audio8_fast vs audio8 on cuda across the same prompts: UTMOS −0.085 (default) / −0.033 (cloning), SIM −0.016, WER *better* by 0.011 — all inside sampling noise at n=4 prompts. `max-autotune` buys ~19x throughput without a measurable quality cost, so the two rows are a clean engine comparison rather than a quality/speed tradeoff.

## Skipped on Apple Silicon (Apple M4, 16 GB)

These models produced no usable output on the Mac M4 bench pass, so they are marked **skipped** on this rig. They stay in the registry — most run on the Windows/Linux CUDA rigs; the gap is Apple-Silicon-specific (no arm64 wheel, MPS memory limits, or no MPS/CPU path at all).

- **luxtts** — **not possible on Apple Silicon.** `ModuleNotFoundError` at load on cpu and mps because `piper-phonemize` never installs: confirmed via `uv` that *no* version of it ships an arm64-macOS wheel (`all versions … no wheels with a matching platform tag, e.g. macosx_*_arm64`) — wheels exist only for Linux (`manylinux_2_28_*`) and Intel Mac (`macosx_*_x86_64`). This is the **same gap as Windows** (no Windows wheel either). Would require building piper-phonemize from source (untested); use Linux instead.
- **mars5** — **not possible (too slow).** Sub-realtime on M4 CPU, exceeds the 600 s per-cell timeout, and has no MPS path (cpu/cuda only). Even with a longer timeout the result would be unusable.
- **vibevoice_15b** — **not viable (GPU-class here).** Runs on cpu with the reference present but at ~0.03–0.07× RTFx and long-form times out; mps OOMs at load (~10.9 GiB). Now tagged GPU-class and skipped on non-CUDA by default — see the per-model entry above. The 0.5B variant (`vibevoice`) runs fine on both.
- **dia**, **qwentts_fast** — CUDA-only; torch reports no available device on Apple Silicon, so the harness builds no cells for them here.

Partial — CPU usable, mps skipped: **zipvoice** cloning (cpu works 10/11 once FFmpeg is present — `brew install ffmpeg` so torchcodec can load the reference; mps OOMs ~20 GiB. It has no default voice, so it only appears under Cloning), **omnivoice** cloning on mps (4/5 with the watermark fix — only the long-form prompt 3 is OS-killed >16 GB; cpu does 5/5; both sub-realtime — see above), and **voxcpm** cloning (600 s timeout; default-voice cpu is fine).
