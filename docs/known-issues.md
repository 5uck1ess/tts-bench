# Known issues

Frictions surfaced while building the harness. None are blockers on Mac/Linux — most apply to Windows or to specific models.

## Cross-cutting

- **`uv venv` doesn't seed pip.** `python -m pip install ...` fails inside a fresh uv venv. Installs use `uv pip install --python <venv-python>` throughout. The install scripts codify this.
- **PowerShell 5.1 + native exes + `$ErrorActionPreference=Stop` is a trap.** `uv` prints to stderr on success (`"Using CPython 3.11.15"`); PowerShell wraps each stderr line as a `NativeCommandError` and trips Stop even on exit 0. `install.ps1` uses `$LASTEXITCODE` checks instead.

- **Two independent "multilingual" fields with different meanings, and nothing compared them — four wrong language cells shipped (fixed 2026-08-15, from [issue #8](https://github.com/5uck1ess/tts-bench/issues/8)).** `harness.MODELS[3]` means *"run canonical prompt 5 (French)"*; `report.MODEL_LANGS` is the README/Capabilities **language cell**. They are different predicates — a zh+en model is genuinely multilingual with the flag `False` — so they were maintained by hand, separately, and drifted in **both** directions. A public bug report caught the first one: `fish_s2` was cell `—` + flag `False`, when the S2-Pro card documents 10M+ hours across **80+ languages** (tier-1 ja/en/zh, tier-2 incl. `fr`), so the row was doubly wrong — understated on the board *and* silently skipping the FR prompt, leaving it with no French clip at all. The audit that followed found three rows wrong the **opposite** way — flag `True`, FR prompt already benched via a real per-language checkpoint, cell claiming English-only: `melotts` (`LANG_CFG` en/es/fr/zh), `neutts_nano` (`REPO_MAP` per-language gguf, en/fr/de/es), `pocket` (`LANGUAGE_CONFIG` en/fr/de/it/pt/es). Those three needed no re-bench — only the cell lied. **Guard added** in `report.py` next to the registry-drift check, enforcing the one direction that is a real invariant: **`multilingual=True` REQUIRES a `✓` cell** (if it synthesizes French on this bench it is multilingual by definition). The converse stays legitimately false and is *not* asserted — `longcat_1b`/`longcat_3p5b`/`miotts_01b`/`miotts_06b`/`wavtts`/`indextts`/`f5tts` are zh+en or en+ja with no French. The guard was verified to fire on the pre-fix state of all three rows rather than assumed to. **Lesson:** a hand-maintained registry that *looks* like it duplicates another field but doesn't is drift waiting to happen — assert whatever implication actually holds, even if it only runs one way. **Follow-up (2026-08-20):** the two remaining *imprecise* (not wrong) cells were tightened to `✓ (zh+en)` — `f5tts` and `indextts`. Worth recording **how**, because the obvious source failed: **neither HF model card states language coverage at all**, so "check the card" would have produced another guess. What settled it was the artifact we actually bench — for `indextts`, the installed `front.py` has exactly two normalizers (`zh_normalizer`/`en_normalizer`) behind a binary `use_chinese()` router and the checkpoint's `bpe.model` vocab is ASCII + CJK-Han with **zero** accented Latin; for `f5tts`, upstream's own mirror is named `F5-TTS_Emilia-ZH-EN` and "more language support" points at community fine-tunes, not the base checkpoint. Both remain `multilingual=False` (no French), which the guard permits. **When the card is silent, the installed code and tokenizer outrank the marketing copy — and the successor model is a trap: the `index-tts` README's multilingual claim (zh/en/ja/es/ar, `lang=` selector) describes IndexTTS-*2.5*, which this bench does not run.**

## Per-model

- **Audio8 0.1B holds its preset voice BETTER than the 0.6B sibling already published with a preset row — but its clone drifts in pitch about as much as `breeze_tts2`.** Benched 2026-08-27 on Win-5090 (3 runs, cpu+cuda, all 5 prompts, both lenses; 21 clips, all health-clean, no failed cells). **Preset stability** (median F0 across the four English prompts, cuda): `audio8_01b` **19.2 Hz / 2.39 semitones**, vs `audio8_fast` 24.7 Hz / 2.95 st and **`audio8` (0.6B) 70.9 Hz / 8.56 st** — controls: kokoro 0.99 st, maya1 1.47 st, vibevoice_15b 2.05 st. So the `_PRESET_AND_CLONE` placement is safe by the standard that put `breeze_tts2` in `NO_PRESET_VOICE` (37.7 Hz / 4.0 st, "no honest preset voice"); the 0.1B clears it comfortably and the **0.6B, already live with a preset row, does not** — worth a look on its own, not changed here. **Exclude the French prompt from this measure:** p5 lifts F0 in both models (0.1B 188 Hz vs 129–148; 0.6B 174 Hz), which is a language effect, not speaker drift — including it inflates the 0.1B to 6.48 st and the 0.6B to 8.56 st. **Cloning** (house `chris_hemsworth_15s`, 91.5 Hz): mean clone F0 **85.6 Hz, −1.14 semitones off the reference**, so it genuinely tracks the target; but the prompt-to-prompt spread is **3.74 semitones**, which sits beside `breeze_tts2`'s 4.0 and behind f5tts 1.5 / echo 1.7 / moss_tts 2.1 / indextts 2.4. Predicts the same shape as Breeze — respectable SIM (timbre is held), middling arena rank (prosody is not). Default and cloning clips are correctly **non-identical** (distinct md5s, default F0 129–188 Hz vs clone 78–97 Hz); identical wavs would have meant the no-reference path was falling back to cloning, the `NO_PRESET_VOICE` signature.
- **Audio8 0.1B carries a DIFFERENT licence to the 0.6B sibling it shares a venv, runner and name-prefix with.** `audio8` / `audio8_fast` (0.6B) are **Apache-2.0**; `audio8_01b` is the **Audio8 Community License v1.0**, a revenue-capped custom licence — 2.1 grants non-commercial use (research, personal, educational, **evaluation**) outright, 2.2 permits commercial use only under **US$2M** annual revenue, above which a separate written licence is required. Redistribution of benchmark *outputs* is unrestricted (there is no output clause at all, unlike the CC-BY-NC rows), so publishing clips and scores is fine. The trap is purely that the family shares a prefix: copying the 0.6B's `"Apache 2.0"` into `MODEL_LICENSE["audio8_01b"]` would have published a false licence on a public board. **Separately, 3 "Responsible Use" forbids using the model "to impersonate individuals without their consent."** That is *narrower* than the Breeze §5(c) clause that forced `breeze_tts2` onto a consent-clean reference — Breeze enumerates "clone, simulate, imitate, or impersonate", Audio8 says only "impersonate", and pairs it with a deception framing plus a disclosure duty the board already satisfies. Whether that difference is load-bearing is a scope call, not a runner detail; see `docs/considered.md`.
- **Audio8 0.1B runs the NAIVE Mamba path on Windows, so its speed row is a floor and it benchmarks SLOWER than the 3.5x larger 0.6B.** The 0.1B's slow AR is a Falcon-H1 hybrid (attention + Mamba); transformers looks for `selective_state_update` / `causal_conv1d_fn` / `causal_conv1d_update` from **mamba-ssm** + **causal-conv1d** and, finding none, logs *"The fast path is not available … Falling back to the naive implementation"* and runs a Python loop over timesteps. Neither package ships a Windows wheel (both build CUDA kernels from source). Output is **correct**, just slow: measured **0.35x RTFx** on a 5090 (canonical prompt 3: 16.95 s of audio in 48.98 s) against the 0.6B base's ~0.7x, and **0.21x** on the 9950X3D CPU (prompt 1: 2.74 s of audio in 13.13 s). Do not read the Windows row as the model's ceiling. **RESOLVED on Linux-3090 2026-08-28** (`mamba-ssm` 2.3.2.post1 + `causal-conv1d` 1.7.0, source build ~11 min, now installed by `install.sh`): the fast path roughly **doubles** the 0.1B — warm cuda mean over the 5 canonical prompts **0.44x -> 0.87x RTFx**, and the naive-fallback warning is gone. But it does **NOT invert the ordering** as predicted here: the 0.6B measures **0.86x** on the same rig, so the 0.1B reaches **parity**, not superiority. Both remain ~10x behind `audio8_fast` (8.42x). Prediction logged as half-right — the penalty and the fix are real, the inversion is not. Prompt 3 lands at ~365 frames against the runner's 1024-frame cap, so the cap is not implicated.
- **Breeze TTS 2 — importing `qwen_tts` DRAINS STDIN, which silently empties every cell in `--stdin` mode.** The runner prints `{"ready": true}`, the harness writes its jobs, and the runner's `for line in sys.stdin` immediately reads EOF: no results, no error, no traceback — the cell just reports nothing, which reads like a timeout or a missing venv rather than a bug. Bisected against the other four imports (`transformers`, `breeze_infer.runtime`, `models.breeze`, `models.fast_streaming`), which are all clean; only `qwen_tts` does it, via the module-level `sox` probe whose subprocess inherits fd 0 and swallows what is queued there. **The fix has to swap fd 0, not `sys.stdin`** — the drain happens in a child process, below the Python level, so rebinding `sys.stdin` alone does nothing. `runners/breeze_tts2_runner.py`'s `_stdin_shielded()` points fd 0 at `os.devnull` across that one import and restores it after. Verified: two jobs in, two `{"ok": true}` lines and two wavs out. **Worth checking on any future model whose venv pulls `sox`** — the same silent-empty-cell signature would appear.
- **Breeze TTS 2 — three more load-time traps, all in the runner docstring:** (1) anything reaching `load_runtime` calls `torch.cuda.set_device`, which rejects a bare `"cuda"` — the harness passes exactly that, so the runner normalises to `"cuda:0"`; (2) `config.json` pins `text_encoder_config.preferred_attn_implementation="flash_attention_2"` and `models/breeze.py` applies it to the text encoder *regardless* of the top-level `attn_implementation=`, so load dies on Windows where flash_attn has no wheel — the runner rewrites that field to `"sdpa"`, which `models/t5gemma2_compat.py` dispatches equivalently through `ALL_ATTENTION_FUNCTIONS` (upstream's README says Linux-only; **nothing in the eager path actually is**); (3) the `ref_edit_tata` template requires an `instruction` field even on the clone path, and omitting it raises `missing template fields: ['instruction']`. It **is** genuinely CUDA-only, though — `models/fast_streaming.py:192` hard-gates on `torch.cuda.is_available()`.
- **Breeze TTS 2 — its clone holds timbre well but pitch loosely: 4.0 semitones of prompt-to-prompt F0 drift vs echo's 1.0 on the SAME reference.** Benched 2026-08-27 against a consent-clean reference (`tym.wav`, median F0 137.0 Hz, cuda, 3 runs, prompts 1–4; French skipped, `multilingual=False`). Breeze's clones land at 150.3 / 136.3 / 125.7 / 119.3 Hz — a 31.0 Hz spread — while `echo` on the identical reference and prompts holds 140.7 / 133.1 / 140.3 / 138.2, a 7.5 Hz spread. **The control matters:** the rest of the cloning board targets `chris_hemsworth_15s.wav` at ~88 Hz, and absolute Hz spread scales with base pitch, so the field's 7.9–12.3 Hz figures are not directly comparable to a 137 Hz reference. Normalising to semitones removes that, and the gap survives: f5tts 1.5, echo 1.7, moss_tts 2.1, indextts 2.4, **breeze_tts2 4.0**. So this is the model, not the reference and not the pitch. It corroborates the by-ear verdict (timbre excellent, flow behind echo) and predicts **high SIM, middling arena rank** — SIM reads timbre, the vote reads prosody. All four clips are health-clean. Warm TTFA 357–440 ms, RTF 0.4–0.5× on a 5090 (eager path).
- **Breeze TTS 2 — it must never be pointed at the house cloning reference; it is benched against a consent-clean one instead.** §5(c)/(d) of the BreezeBlue Research licence prohibit using the model to "clone, simulate, imitate, or impersonate a real person's voice … without that person's explicit and legally sufficient consent", **with no research carve-out** (unlike `higgs_v3`, which affirmatively blesses non-production benchmarking). §4 does permit publishing benchmark results and samples, so the blocker is the *generation* act, not redistribution. Since the model is `NO_PRESET_VOICE`, its no-reference run falls back to `chris_hemsworth_15s.wav`, so there is no configuration that avoids it. **Unblock in progress: the house cloning reference moves to a consent-clean voice Tym records himself.** Note that fixes the same exposure for every cloner on the board, not just this one — but SIM is only comparable within a single reference, so it means re-running the whole cloning lens, not just adding a row.
- **Breeze TTS 2 — on Linux the venv silently resolves a MISMATCHED `torch`/`torchaudio` pair, and it fails at load, not at install.** `install.sh` asked for a bare `torch` with `--extra-index-url .../cu128 --index-strategy unsafe-best-match`. uv took **torch from PyPI (2.13.0, cu130)** while **`torchaudio` — which arrives transitively via `qwen-tts`, not from the explicit list — came off the cu128 extra index at 2.11.0+cu128**. The install reports success. The first generation then dies with `OSError: Could not load this library: site-packages/torchaudio/lib/_torchaudio.abi3.so`, which reads like a corrupt or truncated wheel rather than a version skew, and the runner reports it as a clean `{"ok": false, "error": "load failed: ..."}` cell. **Fix: pin `torch` AND `torchaudio` to the same version, both from the cu128 index** — `install.sh` now pins `torch==2.11.0 torchaudio==2.11.0`, which is also the floor `install.ps1` uses on Windows (`torch>=2.11.0`). Hit on the Linux-3090 2026-08-27. **Worth checking on any model whose venv pulls torchaudio transitively while pinning torch explicitly** — the same install-clean/load-broken signature would appear.
- **`SPEED_ONLY` does NOT filter the per-dir `samples.html`, so a speed-only model's clips still publish under that dir's reference label.** The set's docstring says it is "Filtered out in `_ok_models` (Listen + Scores) and `arena/build_manifest.py` (Arena)" — that is accurate, and it is the whole gap: the top-level `listen.html` correctly shows 0 hits for Breeze TTS 2, but `<dir>/samples.html` is built from the dir's CSV rows and renders **4 Breeze clips with working players** under the heading `cloning · chris_hemsworth voice`. Breeze clones `tym.wav`, a different speaker, so this is exactly the wrong-reference render that putting it in `SPEED_ONLY` was meant to prevent. **Live on BOTH rigs** — `windows-cloning/samples.html` has had it since gh-pages `58b39fe` (2026-08-27), `linux-cloning/samples.html` since `4400305` the same day; the Linux publish matched the Windows precedent rather than introducing this. Fix is to apply the `SPEED_ONLY` filter where `samples.html` is built, not only in `_ok_models`. Until then the same trap applies to `qwentts` and `kokoro_mlx`, whose per-dir sample players are also unfiltered.
- **Breeze TTS 2 — output is duration-deterministic but NOT byte-reproducible across process invocations.** `set_all_seeds(SEED)` is called before every generation and it works where it matters: `audio_s` is identical across all 3 runs of every cell **and** across the default and cloning lenses (1.92 / 5.28 / 17.04 / 8.32 s on the Linux-3090), so there is no state leakage and the warm/cold RTF comparison is sound. The *samples* still differ run to run: two invocations of the identical command gave **correlation 0.999563, max |Δ| 0.024 against an RMS of 0.080, identical sample counts** — the same take with bf16 CUDA kernel noise, inaudible. Note the runner docstring claims "byte-identical duration", which is what actually holds; do not read it as byte-identical audio. Harmless while the model is `SPEED_ONLY` (no clips are scored or arena-paired), but if it ever moves onto the Scores lens its UTMOS/WER/SIM will not be exactly reproducible between runs.
- **Fish Speech S2-Pro — the missing French clip is FIXED (2026-08-20), and the fix needed the GPU emptied in a specific way.** Consequence of the flag bug above: `multilingual=False` meant canonical prompt 5 never ran for `fish_s2`, so it alone among multilingual rows had no French sample while the board already claimed `✓ (80+)`. Now benched on both lenses (cuda, 3 runs) and merged with `merge.py --force`. **It renders French correctly — Whisper transcribes it as an exact match, WER 0.0000** (UTMOS 3.892, SIM 0.5792, health clean). The two sub-average scores are **lens artifacts, not defects**: UTMOS is English-trained so it marks French down, and SIM 0.58-vs-0.71 reflects *cross-lingual* cloning (English reference → French output), which is the same effect recorded for audio8. Three traps worth keeping:
  - **`merge.py --replace` would have destroyed the row.** fish_s2 already had p1–p4, so the duplicate guard fires; `--replace` drops the named model's existing rows **and wavs** before adding. Appending a single prompt to an existing model is `--force`, always.
  - **`gpu-free` reports "GPU free" while ~5 GB is still held.** By design — it evicts only llama-swap's `llama-server` children and never touches other GPU jobs. fish_s2 needs ~20.4 GB of the 3090's 24 GB, so it OOMs against Cicero's residents even when `gpu-free` says the GPU is clear. Worse, killing `audiocpp_server` directly does not hold: the Cicero daemon respawns it in ~2 min and it grabs VRAM **mid-run**, producing an OOM that looks like a capacity problem but is really a race. The sanctioned lever is `~/.cicero/ops/cicerod stop` (STOP sentinel — its own header names "a VRAM test"), kill any orphaned `audiocpp_server`, bench, then `cicerod start`. **Verify comparability afterwards:** the new rows must land at `peak_vram_mb` ~20409, the same as p1–p4; they did.
  - **The default and cloning wavs are bit-identical** (`md5 485d71fed355`) and that is correct, not a mix-up — `fish_s2` is `NO_PRESET_VOICE`, so the runner's no-reference path falls back to the same `chris_hemsworth_15s.wav` with `torch.manual_seed(42)` pinned. Expect identical wavs for any `NO_PRESET_VOICE` model benched on both lenses.
- **`sim_pass` re-populates 20 bogus `qwentts` default SIM cells on EVERY run — re-blank them before committing.** `scoring.sim_pass` scores default-lens clips for `NO_PRESET_VOICE`-style models against the house Chris reference, but Qwen3-TTS Base clones its own bundled `jo.wav`, so the comparison is meaningless: the values come out as noise around zero (−0.10…+0.04, some negative). Because the pass is *missing-only* and the cells are stored blank, every fresh run sees them as missing and refills them. After any `sim_pass`, blank `sim` for all rows where `model` starts with `qwentts` and `mode == "default"`, then confirm `git diff scoring/scores.csv` shows only the rows you actually intended to add. Two mechanical notes: the column is `mode` (not `lens`), and `scores.csv` is **CRLF** — rewrite it with `lineterminator="\r\n"` or the whole file shows as modified.
- **Vaniq-Edge — the shipped `monotonic_align` Cython extension is linux-x86_64 / cp312 ONLY, and `models.py` imports it at module scope.** The HF repo vendors the original `jaywalnut310/vits` tree under `vits_core/`, whose `models.py` does a top-level `import monotonic_align`; that package's `__init__` immediately does `from .monotonic_align.core import maximum_path_c`, and the only build shipped is `core.cpython-312-x86_64-linux-gnu.so`. That is unimportable on Windows, on Apple Silicon, and on **any** Python that isn't 3.12 — including the 3.11 Linux venv the install script creates, so this is not a Windows-only problem and the Linux pass will hit it too. `maximum_path` is used exactly once (`models.py` line 480) inside the **training** forward and never inside `infer()`, so building the extension is unnecessary: `runners/vaniq_runner.py` registers a stub module in `sys.modules` before the import can fire. The stub raises if anything ever calls it, so a future upstream change that genuinely needs the alignment path fails loudly rather than silently degrading. `install.ps1`/`install.sh` skip `vits_core/monotonic_align/build/*` in the snapshot for the same reason.
- **Vaniq-Edge — its whole WER penalty is one prompt, and it decomposes into TWO reproducible defects: utterance-initial /r/ loss, and a mis-phonemized "pytest".** Mean WER 0.1042 (#45 of 59 on the default lens) looks bad next to Inflect-Micro's 0.0303 (#1), but the distribution is lopsided: **p1 and p2 are 0.0000**, and **p3 (0.167) actually beats the board median (0.182)** — most of p3's apparent error is Whisper writing "0.6"/"1.69%" for "zero point six"/"one point six nine percent", a normalization artifact that hits every model equally. **All of the real damage is prompt 4** (0.250 vs a 0.111 board median; 50 of 59 models score better). Diagnosed by transcription rather than inferred:
  - **Not a seed artifact.** The runner pins seed 0 and the duration predictor is stochastic, so the obvious worry is that a bad draw got frozen in. Swept 8 seeds on prompt 4: **every one** garbles the opening (`munpidus` / `munpy does` / `munpyte` / `Munpitis` / `Munpitas` …), WER range 0.167–0.333, **mean 0.271, median 0.278 — and the benched seed-0 value is 0.278, exactly the median.** The published number is representative. (On p3 seed 0 is mildly unlucky — 0.182 vs a 0.167 median, the one seed that renders "Parakeet" as "Carakeet" — but it sits inside the range.)
  - **Defect 1 — utterance-initial /r/ is lost.** `"Run pytest tests slash …"` → `"munpidus test …"`. Prefix any filler and the same word renders correctly: `"Okay. Run pytest …"` → `"Okay, run PyTest …"`, and mid-sentence `"…then run pytest…"` is fine. It reproduces on an unrelated sentence: **`"Run the browser and read my email."` → `"When the browser and read my email."` on 3/3 seeds**, while the canonical prompt 1 (`"Open the browser…"`, same sentence, different first word) is a clean 0.0000. So it is position-dependent, not word-dependent — the model swallows the leading consonant at utterance onset, worst on /r/.
  - **Defect 2 — "pytest" is mis-phonemized regardless of position.** `"The command is pytest."` → **"piteous" / "pietist"** on 3/3 seeds, mid-sentence with a clean onset. This is upstream's `english_cleaners2` → espeak path guessing at an out-of-vocabulary token. Inflect-Micro, which ships its own VITS frontend rather than stock `english_cleaners2`, renders the whole of prompt 4 perfectly (0.0000) — so this is the pipeline's choice, not something inherent to espeak-family frontends.
  - **How to read the row:** the model is clean and near-median on ordinary prose and only breaks on utterance-initial /r/ and unusual tokens. That is also why the by-ear verdict and the metrics disagree — the A/B used prompts 2 and 3, where vaniq genuinely sounds better, and never exercised prompt 4.
- **Vaniq-Edge — `synthesize()` exposes no seed and the duration predictor is stochastic, so unseeded reruns produce different audio LENGTHS.** `config.json` sets `use_sdp: true` (the stochastic duration predictor) where Inflect v2 uses the deterministic one, and upstream's `synthesize(text, length_scale)` takes no seed argument. Measured on canonical prompt 1: two consecutive unseeded calls returned **different sample counts**. In a `--runs 3` cell that means the warm runs would not be generating the same amount of audio as the cold run, quietly corrupting the RTFx comparison against every other row. The runner calls `torch.manual_seed(0)` immediately before each generation; verified bit-identical output (same sample count, same sum) across runs on both cpu and cuda, and the benched cell now reports an identical `audio_s` for all three runs. Any future re-bench or engine variant of this model must keep the seed pin.

- **Scylla's Band — the ten voices differ by 0.53 UTMOS, and the namesake voice is not the best one.** The bundle manifest lists all ten as peers (one style each, all four languages each, no quality or "recommended" field), so there is no in-band signal for which to bench. Measured over the 4 English canonical prompts (`scoring/voice_sweep.py`, Linux, UTMOS + WER): **`ink` 4.348** > tuesday 4.282 > felix 4.252 > orpheus 4.239 > **`scylla` 4.235** > ariadne 4.143 > stone 4.120 > gwen 4.083 > rex 3.989 > max 3.822. That 0.526 spread is wider than the gap between the board's median (~4.05) and its top-8 cutoff (~4.34) — the voice choice moves this model several places on the leaderboard, so it is not an arbitrary pick. **`ink` is the benched default.** Two traps worth naming: (1) `scylla` is the project's *namesake* and the voice in upstream's quick-start, which makes it the intuitive default — it placed **5th, with the 2nd-worst WER (0.1174)**; the name carries no quality meaning. (2) `ink`/`orpheus`/`tuesday` declare `en_gb` as their manifest `default_language`, but rendering them at en_gb makes all three *worse* (ink 4.348→4.205, orpheus 4.239→4.213, tuesday 4.282→4.075). Since all three moved the same direction, that is more likely UTMOS's en_US training bias than genuine degradation — but either way the benched figure is **ink-at-en_us**, which is what the harness's `en → en_us` mapping produces. WER across the ten spans 0.075–0.120 and quantizes hard at n=4 prompts, so treat it as an outlier detector, not a ranking.
- **Scylla's Band — the six affect axes are effectively inert at the default `affect_guidance_scale` of 1.0; you need g≥3 to hear anything.** The emotion control is the model's only real differentiator over other small fixed-voice engines, and at upstream's default it does almost nothing: same voice, same text, `joy=0.75` at g=1 moves mean f0 by **+3 Hz** (182.5 → 185.7) and is inaudible in an A/B. At g=3 it becomes obvious, and the strongest effect is on **duration**, not pitch — `sadness=1.0 g=3` stretches a line to 4.32 s while `anger=1.0 g=3` compresses the same line to 3.40 s, a ~40% swing; `anger=1.0 g=6` lifts f0 by 82 Hz (182 → 265) and raises RMS. This is the documented CFG behavior (the model was trained with 0.15 affect-condition dropout), but anyone evaluating at defaults will reasonably conclude the emotion control is fake — we did, on the first listening pass. The bench's default lens deliberately renders **neutral with no affect set**, so the board shows the model's plain delivery; the affect axes are a feature to reach for, not something baked into the benched clips.
- **Scylla's Band — the single-shot `synthesize()` API cannot render long text; the runner uses `synthesize_stream()`.** The ONNX bundle ships fixed-size graph exports bucketed at 256/384/512/640 latent frames, and anything predicted above 640 raises `ValueError: Predicted 670 latent frames, but this bundle supports at most 640` (the message says "LiteRT bundle" even on the ONNX path — upstream cosmetic bug). Canonical bench prompt 3 predicts 670–705 frames and failed on **every voice**. `synthesize_stream()` is the long-form path: it plans the text into chunks (2 for prompt 3), renders each inside the cap, and emits `audio_chunk` events the runner concatenates. Side benefit: `ttfa_ms` is a real time-to-first-chunk (~2.1 s on prompt 3 vs 3.3 s total) instead of equalling `gen_s`. Note that RTFx *rises* with clip length here, opposite to the usual intuition: benched warm on the 9950X3D it is **4.7× on prompt 1** (2.53 s of audio) but **8.0× on prompt 3** (14.29 s). Fitting the warm runs gives roughly a **0.27 s fixed cost per call plus a ~9.4× marginal rate**, so short lines simply have less audio to amortize the per-call overhead over. Don't quote in-process loop figures for this model — those omit the per-call setup and read ~13–17×, well above what the bench measures.

- **MioTTS — SERVER-BACKED (the bench's second), Linux-only, needs TWO servers up before you bench it; reuses the box's llama.cpp.** MioTTS (`Aratako/MioTTS-*`) is an LLM-codec TTS: a small base LLM (GGUF) emits MioCodec tokens that a MioCodec torch model decodes to a **44.1 kHz** wav. Like higgs_v3 the runner loads no model — `runners/miotts_runner.py` is a thin HTTP client (venv = `requests`+`soundfile`+`numpy`, **no torch**, so it's in `SERVER_BACKED` → the harness probes the GPU via `nvidia-smi`, not a venv torch import). Standup (Linux + CUDA): (1) **LLM server** — reuse the box's `llama-server -hf Aratako/MioTTS-GGUF -hff MioTTS-0.6B-BF16.gguf --port 8000`; (2) **MioTTS REST orchestrator** — clone `Aratako/MioTTS-Inference` into `venvs/miotts/src`, `uv sync`, `python run_server.py --llm-base-url http://localhost:8000/v1 --port 8001` (downloads `MioCodec-25Hz-44.1kHz-v2` on first run). Full recipe in `install.sh`'s miotts stanza. Differences from higgs_v3 worth noting: (1) **cloning reference is base64 in-band** (`POST /v1/tts` `reference.type="base64"`) — **no Docker bind-mount and no sibling `.txt` transcript** (the win over higgs/cosyvoice); the pure-cloner default-lens path clones the house `chris_hemsworth_15s.wav`, so MioTTS is in `NO_PRESET_VOICE` (cloning board only). (2) **One GGUF per server session** — a single GPU hosts one GGUF at a time, so the two sizes (`miotts_01b`/`miotts_06b`, which share runner+venv+servers; `--variant` is labeling only) bench in **separate passes**: start the LLM server on the 0.6B GGUF, bench `miotts_06b`, restart it on the 0.1B GGUF, bench `miotts_01b`. (3) `peak_vram_mb` is `None` (model lives in the servers); coarse whole-GPU `gpu_used_mb` via `nvidia-smi`. (4) Non-streaming, so `ttfa_ms == gen_s`. Licenses: code MIT; 0.6B = Apache-2.0, 0.1B = Falcon-LLM. EN/JA.
- **DramaBox — CUDA-only (~18 GB VRAM), expressive *dialogue* TTS on an LTX-2.3 video-model backbone; short prompts get heavy silence padding (trimmed in the runner).** DramaBox (`ResembleAI/Dramabox`, 3.3B audio-only DiT, IC-LoRA fine-tune of LTX-2.3) is a source-clone install (no PyPI): the runner imports `src.inference_server.TTSServer` from `venvs/dramabox/src`, fetches the DiT + audio-components + a 4-bit Gemma-3-12B text encoder via the repo's `model_downloader` (~16 GB, HF-cached), and builds the server with explicit `checkpoint`/`full_checkpoint` paths + `compile_model=False` (the bare `TTSServer()` defaults to non-existent local `models/` files, and torch.compile/Triton is brittle on Windows). bitsandbytes (the 4-bit Gemma) *does* ship a working Windows wheel (0.49.2 on the 5090). Peak VRAM ~18 GB (audio-only mode frees LTX's video stack) → fits both the 5090 and the 3090. 48 kHz out (LTX "BWE" bandwidth-extension decode). Prompt grammar is `<speaker description>, "<dialogue>" <action>`; the runner wraps plain bench prompts in a neutral `A person speaks clearly, "…"`. Watermarked (Resemble Perth). **Gotcha:** DramaBox's duration estimator over-allocates for short lines, so a clip can open with several seconds of dead air — the runner trims leading/trailing silence (energy < −40 dB rel. peak, 0.1 s pad) so `audio_s`/RTFx aren't inflated. The optional RE-USE voice-ref denoiser (mamba-ssm) is skipped (no Windows wheel; off by default). Both lenses: no-reference = prompt-described voice (Default), 10 s+ wav = cloning.
- **dots.tts — CUDA-only 2B continuous AR TTS; the sampler MUST be seeded or it early-stops to a ~0.3s fragment.** dots.tts (`rednote-hilab/dots.tts`, Apache-2.0) is a pip package (`dots_tts`) source-clone editable install; the runner does `from dots_tts.runtime import DotsTtsRuntime` and `from_pretrained("rednote-hilab/dots.tts-soar", precision="bfloat16")` (the SCA flagship — best Seed-TTS-Eval quality; weights snapshot-download from HF on first run, ~5.3 GB VRAM at bf16, fits the 3090). **Gotcha:** the AR + flow-matching head hits an early end-of-audio if the RNG isn't seeded — an unseeded run emitted only 2 audio patches (15360 samples = 0.32 s) for a full sentence. The CLI/gradio both call `seed_everything()` before generating; the runner mirrors this (`seed_everything(42)` before each `generate`), after which "Open the browser and read my email." renders at the expected ~1.9 s. Sampler params follow the upstream **CLI** defaults (`guidance_scale=1.2`, `num_steps=10`, `speaker_scale=1.5` default) — NOT the README quick-start's `guidance_scale=1.0`, which is below the runtime default. Multilingual (24 langs incl. FR), 48 kHz. **Rig note — LINUX-ONLY.** The Windows install never worked — its `WeTextProcessing`→`pynini` dependency won't build under Windows MSVC (`cl` rejects pynini's GCC/Clang `-Wno-register` flag → `D8021`), and that import is hit at module load (`runtime.py` → `utils.text` → `tn`) so it can't be skipped — so dots.tts has **no `install.ps1` stanza** and is benched/published from the **Linux-3090** only. **Default voice — it has one, but it varies.** dots.tts *does* synthesize with no reference (it's not reference-only), but that own-voice is sampled fresh per prompt — a different speaker each generation, exactly like Higgs v3 — so it's NOT in `NO_PRESET_VOICE`; it shows in the Default-voice gallery with a "⟳ voice varies" badge, and under Cloning (consistent) when given a reference. Revisit `install.ps1` only if a working Windows path is found.
- **Zonos2 — Linux + CUDA only; pure zero-shot cloning through the in-process `TTSLLM.generate_one` API.** Zonos2 (`Zyphra/Zonos2`, Apache-2.0) supersedes Zonos v0.1 (`zonos`). It is an **8B sparse MoE (~900M active)** model with a **44.1 kHz** DAC output and no preset voice: `TTSLLM.embed_speaker_file()` embeds the reference and `TTSLLM.generate_one()` performs zero-shot cloning in-process. Upstream ships compiled CUDA kernels, so it has no CPU/MPS or Windows path and is installed only on the Linux-3090: git clone the source into `venvs/zonos2/src`, then `uv sync` it into the harness venv. It is therefore in every `NO_PRESET_VOICE` list and appears only under Cloning.
- **Twenty-one zero-shot models have no "default voice" — their no-`--reference` run clones the bundled reference.** `moss_tts`, `moss_tts_v15`, `moss_tts_nano`, `fish_15`, `fish_s2`, `metavoice`, `openvoice`, `zipvoice`, `zonos`, `zonos2`, `vibevoice_15b`, `vibevoice_7b`, `echo`, `qwentts`, `qwentts_06b`, `qwentts_fast`, `f5tts`, `indextts`, `step_editx`, `neutts_air`, `neutts_nano`, `luxtts` ship no preset/built-in speaker. With no `--reference` they fall back to `reference/chris_hemsworth_15s.wav`, so their "default voice" bench sample is just a (different, non-deterministic take of a) Chris clone — not a real default. The published Listen gallery therefore shows these models **only under Cloning**, never in the Default-voice section. Models that *do* ship a default — `styletts2` (bundled LibriVox speaker), `vibevoice` 0.5B (`en-Emma_woman` preset), ChatterBox, etc. — stay in Default normally.

- **Audio8 TTS — the compiled fastpath needs `triton-windows` on Windows, and its upstream `max_new_tokens=400` default silently truncates long prompts.** Two traps, both load-bearing. (1) **Triton.** `audio8_fast` runs the ScrappyLabs `fast_arktts` static-shape rewrite under `torch.compile(fullgraph=True, dynamic=False)`. PyPI `triton` is Linux-only, so on Windows the first attempt dies with `TritonMissing` and, if you fall back to `compile_mode=None`, you get **eager speed wearing the compiled label** (RTFx 0.71 — indistinguishable from the `audio8` base row). `uv pip install triton-windows` fixes it (3.7.1 against torch 2.11.0+cu128); this is the same wall that forced `compile_model=False` on DramaBox, and it *is* beatable. Linux needs no such wheel. (2) **The 400-frame cap.** `FastTTS` defaults to `max_new_tokens=400`, and because shapes are static that cap is baked into the compiled graph. The codec runs ~21.5 frames/s, so 400 frames is an **18.6 s ceiling** — and canonical bench prompt 3, cloned, measured **390 frames** on this rig. A ten-frame margin before silent truncation. The runner uses **1024** (~47 s). That does not slow generation (the loop still exits at EOS) but it does widen per-frame attention, so our RTFx is *conservative* against upstream's 400-frame figures. (3) **Compile cost is front-loaded, then cached.** First-ever `max-autotune` build is ~370 s; inductor caches to disk, so a fresh process afterward is ~50 s end-to-end. Compilation happens at load (`warmup=True`), i.e. outside the timed generate window — the same accounting as `qwentts_fast`'s CUDA-graph capture. Measured engine delta on the same weights (Win-5090): eager **0.71x** -> `default` compile **2.53x** -> `max-autotune` **15.06x**, a ~21x win versus upstream's advertised 5.8x (they benchmarked a 5090 *Laptop* at ~576 GB/s).

- **Audio8 TTS — clones English well and largely loses the voice in French; it tops the cloning board on naturalness while sitting mid-pack on speaker similarity.** Two separate findings from the Linux scoring pass, both easy to misread. (1) **The French cliff.** Per-prompt cloning SIM against the Chris reference: p2 **0.708**, p4 **0.704**, p3 **0.678**, p1 0.558 (short line, less material to match) — and canonical prompt 5, the French one, **0.363**. UTMOS drops with it (3.91 vs a 4.38 English mean). So the model reproduces a reference voice acceptably within English and mostly abandons it when asked to speak French in that voice. This is why `audio8`/`audio8_fast` are deliberately **not** in `report.py`'s `MODEL_CROSSLINGUAL` — that registry wants positive evidence of clone-in-one-language / speak-another, and here the evidence points the other way. Note the model is still legitimately `multilingual=True`: its *default-voice* French is fine, and the FR prompt runs. Cross-lingual **cloning** is the specific thing that fails. (2) **Naturalness and similarity disagree, and it matters which one you quote.** On English cloning prompts audio8 is **#1 of 43 on UTMOS** (4.382, with audio8_fast #2 at 4.373 — ahead of styletts2, higgs_v3, chatterbox) but only **#19/#20 of 43 on SIM** (0.665 / 0.655, against longcat_1b 0.870 / echo 0.836 / omnivoice 0.835). It produces the cleanest-sounding cloned audio on the board that doesn't especially sound like your reference. By-ear QA agreed on the pleasant part, which is exactly the trap — pick the metric that matches the question being asked. (3) **The compiled engine is not the cause of any of this.** audio8_fast vs audio8 on cuda across the same prompts: UTMOS −0.085 (default) / −0.033 (cloning), SIM −0.016, WER *better* by 0.011 — all inside sampling noise at n=4 prompts. `max-autotune` buys ~19x throughput without a measurable quality cost, so the two rows are a clean engine comparison rather than a quality/speed tradeoff.

- **Sopro V2 Turbo — utterance duration is sampling-variable by ~30%, so a single-run duration or RTFx comparison between the two variants means nothing.** Sampling runs at upstream defaults (temperature 0.8 / top_p 0.9 / top_k 25) and the model chooses its own pacing, so the same sentence lands anywhere in a wide band. Measured on canonical prompt 2, cuda, chris reference, seeds 0-4 — on **2.0.5**: offline 5.49 / 5.74 / 6.12 / 6.82 / 7.24 s and streaming 5.02 / 5.54 / 5.96 / 6.39 / 8.82 s; re-measured on **2.2.0**: offline 5.49 / 5.92 / 6.16 / 6.77 / 8.27 s (50% spread) and streaming 5.58 / 5.79 / 6.43 / 6.69 / 7.41 s (33%). The two distributions overlap almost completely in both versions, and the spread did not shrink with the fixes. The first seeded A/B looked like the streaming path spoke 54% slower (8.82 s vs 5.74 s at seed 0); it was an outlier, not an engine property, and four more seeds killed the hypothesis. Because `audio_s` moves, so does RTFx. The runner therefore pins `torch.manual_seed(0)` (plus `cuda.manual_seed_all`) before **every** generation, which makes reruns bit-reproducible — verified: `audio_s` is identical to 6 decimal places across 3 consecutive runs. Never compare a sopro duration against a sibling row without that seed pinned.
- **Sopro V2 Turbo — no preset voice at all, and the no-reference path raises rather than silently substituting one.** `synthesize()` with neither `ref` nor `ref_audio_path` raises `ValueError("provide ref or ref_audio_path")`; there is no bundled default speaker. Both rows are therefore `kind=cloning` and live in `NO_PRESET_VOICE` (cloning lens only). The runner borrows `reference/chris_hemsworth_15s.wav` when `--reference` is omitted, matching the 27 other runners that do the same, so the default lens still yields a comparable speed row instead of a failure cell. Note `reference/*.wav` is gitignored, so the fallback only resolves in a real working copy — never in a bare worktree.
- **Sopro V2 Turbo — the two rows are one checkpoint run at two generation granularities, and only the streaming row's TTFA is a real latency.** Until 2.1.1 the split was also a *vocoder* split (`vocoder.safetensors`, 14-layer non-causal, vs `vocoder_streaming.safetensors`, causal with 3 frames of lookahead). **Since 2.2.0 there is one unified causal Vocos** (8 layers, lookahead 3) and `vocoder_streaming.safetensors` is gone from both the package and the HF repo, so the variants now differ only in `synthesize()` (whole waveform) vs `stream()` (64-frame chunks). The paths are still not bit-exact. Measured warm on the 5090, cloning lens, median over prompts 1-5: offline **RTFx 19.2x with `ttfa_ms == gen_s`** (non-streaming, so that number is not a latency), streaming **TTFA 119 ms at RTFx 11.7x**. `prepare_reference()` is hoisted out of the timed region — that matches upstream's own published methodology, which explicitly precalculates the reference to reach its ~200 ms TTFA claim. CPU is genuinely viable: ~2.7x realtime on the 9950X3D (both variants), ~1 GB VRAM on cuda.

- **Sopro V2 Turbo — upstream ships weight changes without a package version bump, so a stale HF cache silently keeps you on old audio.** The 2.0.5 rows were measured on HF revision `0abc5561`; `model.safetensors` was then re-uploaded (2026-08-30) and both vocoders replaced by a shared official Vocos (2026-09-01), landing on `f747f9edfb7b0233a3b7105af3a75603a7213d26`. `from_pretrained` takes whatever `main` holds and no runner here pins `revision=`, so the only way to know which checkpoint a row was measured on is to record the SHA — read `~/.cache/huggingface/hub/models--samuel-vitorino--sopro-v2-turbo/refs/main` before and after the first load. The reverse trap is worse: **2.2.0 is a hard floor, not a preference** — the current artifacts fail to load on `<=2.1.1`, which still expects `vocoder_streaming.safetensors`, and upstream's own README now carries that compatibility notice.

- **Sopro V2 Turbo — the 2.1.0→2.2.0 upstream fixes moved both loudness and speed, so 2.0.5 rows are not comparable to 2.2.0 rows.** Two defects were fixed: (1) `normalize_reference` clamped reference gain symmetrically (`±REF_GAIN_LIMIT_DB`), attenuating loud references, and streaming derived its output gain from a *fixed* `PROMPT_LEVEL_DB` rather than the reference's actual level — so offline and streaming came out at different loudness. 2.2.0 is boost-only, peak-guarded at 0.95, and derives streaming gain from `ref.level_db`. Measured effect on the same prompts: RMS rose from 0.074-0.093 to 0.095-0.132, and the offline/streaming RMS gap closed (p2: 0.076/0.093 → 0.1305/0.1316). (2) The vocoder was band-limited (2.1.1) then replaced with the unified 8-layer Vocos (2.2.0), which is also **why every speed number improved**: warm cuda RTFx 14.2x→18.9x offline and 8.9x→12.6x streaming, warm CPU 1.8x→2.8x and 1.5x→2.7x, streaming cuda TTFA 132 ms→109 ms. Health stayed clean (0 flags on 40 wavs both times), but `clip_frac` went from exactly 0 to ~1e-5 — a handful of samples now touch full scale, well under the flag threshold.
- **Sopro V2 Turbo — `pip install torch --index-url .../cu128` silently no-ops on Windows, because `sopro` already dragged in the CPU wheel.** The package depends on `torch>=2.3`, so PyPI's Windows CPU-only build is installed first and uv then considers the requirement satisfied: the cu128 install reports `Checked 2 packages` and changes nothing, leaving `2.13.0+cpu` and `cuda.is_available() == False`. The working form is `uv pip install --reinstall-package torch --reinstall-package torchaudio torch torchaudio --index-url https://download.pytorch.org/whl/cu128`, which lands `2.11.0+cu128`. Linux needs none of this (PyPI torch is already CUDA-enabled there). Also pin the package: `sopro` shipped **five patch releases in the 11 hours** after v2 launched (2.0.0 at 00:45 UTC to 2.0.5 at 11:22 UTC on 2026-08-27); the bench pinned `sopro==2.0.5` at first and moved to `sopro==2.2.0` on 2026-09-04, when upstream shipped the loudness and vocoder fixes. Unrelated-but-confusable: the board already has a `soprano` row, a different model entirely.

- **sanoTTS `heart-nano` cannot say canonical prompt 3 — a hard 207-phoneme-token cap that is NOT a raisable knob.** The nano voice raises `sanotts.FrontendError: phoneme sequence has 285 tokens including BOS/EOS; maximum is 207` on bench prompt 3. Measured ceiling on that text: **184 of its 253 chars** (~73%); prompts 1, 2 and 4 all pass, so the row publishes 3 of the 4 English cells (canonical prompt 5 is French and never runs for an English-only model). Two things make this a genuine limit rather than a configuration mistake, and both were checked in the installed package rather than assumed. **(1) The cap is trained-in, not a safety margin.** `engine.py` reads it from the voice pack (`NANO_DUR_MAX_TOKENS`, default 207 in `nano_frontend.py`), and `models.py` then feeds that exact value into the duration model as `length_hint = log1p(n)/log1p(max_tokens)` — so raising the cap re-scales the conditioning feature for *every* input and would silently corrupt timing everywhere, not just past 207. This is the **opposite** of the `audio8_01b` situation, where the cap was a decode ceiling and lifting it cost only memory; do not generalize that fix here. **(2) Upstream ships no long-form path.** Neither `cli.py` nor `engine.py` chunks or sentence-splits, so unlike `scyllasband` — whose identical-looking fixed-bucket failure was solved by the vendor's own `synthesize_stream()` — there is nothing to switch to. Chunking it ourselves would invent a capability the model does not have and make the row incomparable to its neighbours, so **the cell is left to fail** (precedent: `kokoro_mlx`'s prompt-2 crash publishes as a failed cell). `sanotts_amy` is unaffected — the piperlite path is uncapped and rendered 761 chars (53.0 s of audio) in one call without complaint.
- **sanoTTS — the module-level `sanotts.synthesize()` reloads the voice pack on every call, which would destroy the warm column.** `sanotts.synthesize(text, voice=...)` is a convenience wrapper that constructs a fresh `Synthesizer` each time (its own docstring says so). Benching through it makes run 1, 2 and 3 all cold, and the cold/warm split — the thing that detects state bugs across runs — silently becomes meaningless. `runners/sanotts_runner.py` builds one `Synthesizer` at load time and reuses it. The cost is visible in the first smoke pass: amy's first call measured **2.07 s** for prompt 2 against **0.39 s** warm for the same text, i.e. ~1.7 s of that is pack loading, not synthesis.
- **sanoTTS speed rows are the numpy path — do not read them as the "$3 chip" numbers.** Upstream's headline RTF figures (0.225 on an ESP32-S3; ~0.003–0.039 in the audio.cpp CPU table) come from the hand-written C/WASM runtime. The bench measures the pure-numpy Python package, which is a different implementation of the same weights. Both are still comfortably faster than realtime on the 9950X3D — warm CPU, amy renders 17.98 s of audio in 1.19 s (**~15x**) and heart-nano 6.10 s in 0.055 s (**~110x**) — but the numbers are not comparable to the MCU claim in either direction.
- **sanoTTS voices download on first use, so the first bench cell would otherwise time an HTTP fetch as model load.** `pip install sanotts` ships no weights; packages are pulled from `huggingface.co/ampixa/sanoTTS` into `~/.cache/sanotts/` on first use (GitHub `voices-v1`/`voices-v2` releases are the fallback; `SANOTTS_VOICE_SOURCE=hf|github` pins one). Warm each benched voice once before a canonical run. Both benched voices are deterministic — repeated calls are byte-identical, including the noise-fed nano decoder, which seeds itself from `DEFAULT_NANO_SEED`.
- **sanoTTS `MODEL_LANGS` says `— (en)` even though the family covers six languages.** The project ships 11 voices across en/ne/hi/vi/id/zh, but the two rows we bench (`amy`, `heart-nano`) are English-only voices, and that column describes the benched artifact, not the family. It is also why both rows carry `multilingual=False`: the bench's only non-English canonical prompt is **French**, which sanoTTS does not support at all, so there is no prompt that would exercise the other five languages. This is the legitimate direction of the `report.py` guard (which asserts only that `multilingual=True` requires a `✓` cell).
- **sanoTTS's own comparison table cites Inflect Nano at 4.63M; we compute 3.96M.** Their README ranks `sanoTTS (amy)` above `Inflect Nano` and `Kitten TTS nano` — both live rows here — using a 4.63M figure for Inflect Nano, where `MODEL_SIZE` carries 3.96M (deployed params, per the param-count sourcing rule: from the card or computed over the weights, never copied from a sibling). The gap is probably deployed-vs-total params. It does not change their ordering claim, but do not silently adopt their number, and expect the discrepancy to come up if the comparison is ever quoted publicly.
- **sanoTTS's headline UTMOS ranking does not survive our own scoring pass — the Inflect Nano comparison inverts, and the KittenTTS win is a wash.** Their README's viral claim is `sanoTTS (amy)` **4.10** > `Inflect Nano` **3.65** > `Kitten TTS nano` **3.58**, over a 24-sentence set. On our Scores board (`scoring/score_all`, UTMOS22, 2026-09-05) the same three models read **amy 3.821**, **Inflect-Nano v2 4.354**, **KittenTTS Nano 0.1 3.665** — each the mean of the same four English prompts, one board-picked clip per prompt (`publish._pick_clip`: windows-default first, cuda over cpu). The Inflect Nano half **inverts outright**: it beats amy by **0.53** rather than losing to it by 0.45, and ranks **8th of 40** on the Default board against amy's **30th of 40**. The KittenTTS half does not reproduce as a win worth citing: amy's margin is **0.155**, and it is three prompts up / one down (amy loses p3, 3.768 vs 4.062) inside KittenTTS's own 0.63 per-prompt spread — call it a wash, not a win. `sanotts_heart_nano` is **40th of 40** (2.154), last on the board, which is an unremarkable result for 294K params. **Three caveats, all of which have already caught someone here.** (1) This is **not** a refutation of their absolute numbers: their 24-sentence set and UTMOS build are not ours, so the only defensible statement is the *ordering within one consistent harness* — never quote our 3.821 against their 4.10 as though they were measured alike. (2) **Quote the board-picked means, not raw `scores.csv` means.** Averaging every row gives inflect_nano 4.40 / kittentts 3.69, because the CSV carries the same four prompts rendered up to four times (linux+windows x cpu+cuda); those numbers appear nowhere on the board and an earlier draft of this entry shipped them. The differing row counts per model are duplicate renders, **not** broader prompt coverage. (3) There is **no clean per-prompt separation** from Inflect Nano — its weakest board-picked prompt (p2, **4.1156**) sits just *below* amy's best (p1, **4.1382**). The separation is in the means, not every prompt; claiming per-prompt dominance overstates it. WER is the quieter caveat: amy is clean on short prompts (0.000/0.000) but hits **0.212 on canonical prompt 3**, the long technical one, for a 0.067 mean.

## Skipped on Apple Silicon (Apple M4, 16 GB)

These models produced no usable output on the Mac M4 bench pass, so they are marked **skipped** on this rig. They stay in the registry — most run on the Windows/Linux CUDA rigs; the gap is Apple-Silicon-specific (no arm64 wheel, MPS memory limits, or no MPS/CPU path at all).

- **luxtts** — **not possible on Apple Silicon.** `ModuleNotFoundError` at load on cpu and mps because `piper-phonemize` never installs: confirmed via `uv` that *no* version of it ships an arm64-macOS wheel (`all versions … no wheels with a matching platform tag, e.g. macosx_*_arm64`) — wheels exist only for Linux (`manylinux_2_28_*`) and Intel Mac (`macosx_*_x86_64`). This is the **same gap as Windows** (no Windows wheel either). Would require building piper-phonemize from source (untested); use Linux instead.
- **mars5** — **not possible (too slow).** Sub-realtime on M4 CPU, exceeds the 600 s per-cell timeout, and has no MPS path (cpu/cuda only). Even with a longer timeout the result would be unusable.
- **vibevoice_15b** — **not viable (GPU-class here).** Runs on cpu with the reference present but at ~0.03–0.07× RTFx and long-form times out; mps OOMs at load (~10.9 GiB). Now tagged GPU-class and skipped on non-CUDA by default — see the per-model entry above. The 0.5B variant (`vibevoice`) runs fine on both.
- **dia**, **qwentts_fast** — CUDA-only; torch reports no available device on Apple Silicon, so the harness builds no cells for them here.

Partial — CPU usable, mps skipped: **zipvoice** cloning (cpu works 10/11 once FFmpeg is present — `brew install ffmpeg` so torchcodec can load the reference; mps OOMs ~20 GiB. It has no default voice, so it only appears under Cloning), **omnivoice** cloning on mps (4/5 with the watermark fix — only the long-form prompt 3 is OS-killed >16 GB; cpu does 5/5; both sub-realtime — see above), and **voxcpm** cloning (600 s timeout; default-voice cpu is fine).

## Per-model licenses

**Each TTS model has its own license** — check the linked upstream repos before deploying any of them in a product.

- MIT: [Pocket-TTS](https://github.com/kyutai-labs/pocket-tts), [Piper](https://github.com/OHF-voice/piper1-gpl), [ChatterBox](https://github.com/resemble-ai/chatterbox), [F5-TTS](https://github.com/SWivid/F5-TTS), [VibeVoice (community fork)](https://github.com/vibevoice-community/VibeVoice), [Supertonic](https://github.com/supertone-inc/supertonic) (sample code; model weights are **OpenRAIL-M**, see below)
- **OpenRAIL-M (use-based, commercial-permissive):** [Supertonic model weights](https://huggingface.co/Supertone/supertonic) — read the license for the use restrictions.
- Apache 2.0: [NeuTTS](https://github.com/neuphonic/neutts), [Kokoro](https://github.com/hexgrad/kokoro), [KittenTTS](https://github.com/KittenML/KittenTTS), [LuxTTS](https://github.com/ysharma3501/LuxTTS), [dots.tts](https://github.com/rednote-hilab/dots.tts) (code + released checkpoints incl. dots.tts-soar; outputs free to publish)
- **CPML 1.0 (non-commercial):** [Coqui XTTS-v2](https://huggingface.co/coqui/XTTS-v2) — research / personal use only. The harness auto-accepts via `COQUI_TOS_AGREED=1`.
- **CC-BY-NC-SA-4.0 (non-commercial — applies to the generated audio, not just the weights):** [Echo-TTS](https://github.com/jordandare/echo-tts), [Fish Speech 1.5 / S2-Pro](https://github.com/fishaudio/fish-speech). Echo's *output* license is forced to CC-BY-NC-SA-4.0 by its [Fish S1-DAC autoencoder](https://huggingface.co/jordand/fish-s1-dac-min) dependency — the same mechanism that makes Fish Speech's own outputs CC-BY-NC-SA — so clips from any of these are non-commercial regardless of how the rest of your stack is licensed.
- **NVIDIA Open Model License:** [Magpie-TTS Multilingual 357M](https://huggingface.co/nvidia/magpie_tts_multilingual_357m) — commercial use permitted with terms; HF accept-terms gated.
- **LTX-2 Community License:** [DramaBox](https://huggingface.co/ResembleAI/Dramabox) — non-commercial (commercial use requires a separate Commercial Use Agreement from the LTX-2 licensor, Lightricks). Llama-style community license: no "no-benchmarking" clause and redistribution is permitted, so non-commercial benchmarking + publishing sample clips here is allowed. Built on Lightricks LTX-2.3; outputs are watermarked (Resemble Perth).
- **Boson Higgs Audio v3 Research and Non-Commercial License:** [Higgs Audio v3 TTS](https://huggingface.co/bosonai/higgs-audio-v3-tts-4b) — non-commercial. *Explicitly* permits "non-production benchmarking, evaluation … by commercial entities" and says publication of benchmark outputs / illustrative samples in blog posts, public model cards, or non-commercial repositories is **not** a Commercial Purpose — so benchmarking here and publishing sample clips on the public leaderboard is allowed. Download is HF accept-terms gated (export `HF_TOKEN` before `sgl-omni serve`).
- **CC-BY-NC (non-commercial weights):** [OmniVoice](https://github.com/k2-fsa/OmniVoice) — the code is Apache 2.0, but the pre-trained model weights are **CC-BY-NC** due to constraints from its Emilia training data (same mechanism as WavTTS). No commercial use of the model. Reclassified 2026-07 after the upstream card was changed from Apache 2.0 (see [HF discussion #29](https://huggingface.co/k2-fsa/OmniVoice/discussions/29) and [GitHub issue #211](https://github.com/k2-fsa/OmniVoice/issues/211)).
- **GPL-3.0 (copyleft — with an MIT runtime carve-out):** [sanoTTS](https://github.com/Ampixa/sanoTTS) — the HF weights are tagged `gpl-3.0` and the project as a whole is GPL-3.0-or-later, but the **inference runtime and language bindings** (`mcu/src/snt_*.c`, `mcu/include/`, `mobile/`) are dual-licensed **MIT** (`LICENSE.MIT`), and the PyPI `sanotts` package we install declares MIT. The copyleft comes from **espeak-ng** alone, which supplies grapheme-to-phoneme; upstream audited the boundary and none of the MIT runtime files reference espeak. So the runtime can be embedded permissively, but the G2P cannot be taken without GPL-3.0. Benchmark outputs are unaffected — GPL does not reach a program's output — which is why this clears the redistribution bar the same way the board's existing GPL-3.0 and AGPL-3.0 rows do.
- **Check upstream — see model repo:** [VoxCPM](https://github.com/OpenBMB/VoxCPM). License field is not stated in the standard MIT/Apache form in the upstream README — verify before deploying anywhere production-adjacent.

For the models in the [Considered but skipped](considered.md) section: Fish Audio S2 is research-license non-commercial, Fish Audio S1-mini is CC-BY-NC-SA-4.0, Orpheus TTS is Apache 2.0, CosyVoice 3 see upstream — all explicitly outside this bench but listed there so the reasoning is documented.
